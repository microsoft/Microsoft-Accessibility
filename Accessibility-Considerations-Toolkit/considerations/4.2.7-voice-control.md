# FPS 4.2.7 — Usage with limited manipulation or strength (voice control)

Where ICT requires manual actions, the ICT provides features that enable users to make use of the
ICT through alternative actions not requiring manipulation, pinching, or twisting of the wrist, or
simultaneous actions.

Evaluate paths operated entirely through voice control, without keyboard, mouse, trackpad, or
touchscreen fallback. These input exclusions define a test context, not anyone's overall abilities.
See the companion consideration file (4.2.7-keyboard-interaction.md) for keyboard-only evaluation.

## Evaluation Considerations

Evaluate label-based activation, fallback navigation, and dictation with Windows Voice Access, macOS
Voice Control, iOS Voice Control, or Android Voice Access. Test without manual keyboard, mouse,
trackpad, or touchscreen input. Assess visual-label requirements where visual targeting is used,
without assuming clear vision, comprehension of the layout, or absence of other access requirements.

Label-based voice control activates elements through spoken labels, for example "click Submit" for a
button labeled "Submit." Matching visible text and the programmatic accessible name supports this
path; mismatches or missing labels may require less efficient alternatives. Confirm actual command
behavior on the platform rather than inferring success from a screenshot.

Iconography may also suggest a spoken label: a gear icon may prompt "click Settings," which requires
an accessible name including "Settings" for that label-based path. "Preferences" or "cog-icon-btn"
may instead cause a mismatch. Icon interpretation varies; evaluate visible text or discoverable
explanations rather than assuming everyone translates an icon identically.

Evaluate **number overlays** ("show numbers", then a spoken number) when label activation fails, and
verify which controls receive numbers. Triggering and scanning the overlay adds effort. For
unnumbered canvas regions or unlabeled areas, test **grid navigation**, subdividing a numbered grid
until the target is reached. This last-resort path commonly adds the most commands; fallback
preferences and performance vary.

For each screenshot or interface, consider:

- Does every interactive element have a VISIBLE TEXT LABEL that matches its accessible name?
  Icon-only buttons, controls labeled only by proximity, and elements whose visible text doesn't
  match their programmatic accessible name are all barriers.
- Can all interactions be completed by CLICKING elements? Drag-and-drop, click-and-hold, drawing,
  gesture-based interactions, and slider manipulation are difficult or impossible by voice.
- Are interactive elements VISUALLY DISTINGUISHABLE? The user needs to identify what's clickable to
  know what to say. Elements that look like static text but are actually interactive (links styled
  as plain text, clickable divs) are undiscoverable.
- How many UNLABELED or ICON-ONLY elements need number overlays rather than reliable label commands?
  Test the fallback burden rather than assume every icon requires it.
- Are there CUSTOM WIDGETS that require complex pointer interactions (drag-and-drop, canvas drawing,
  multi-touch gestures)? These need voice-operable alternatives.
- Are there TEXT INPUT areas? The user dictates text — does the interface handle dictation input
  well (autocorrect interactions, cursor positioning)?

Possible barriers include icon-only buttons with missing or mismatched names, drag-and-drop as the
sole path, sliders without keyboard/text alternatives usable by voice, hover-only controls where
hover is unavailable in the configured voice path, canvas interfaces without voice alternatives,
CAPTCHAs without a voice-compatible audio or other alternative, dictation interference (aggressive
autocorrect, auto-advancing fields), and visible-label/name mismatches.

Ground findings in labels, accessible names, and tested voice commands. Clear visible labels
matching accessible names support voice operability; voice use does not establish visual
comprehension, speech capability in every setting, or the absence of other disabilities.

## Assistive Technologies

### Windows Voice Access

**Category**: voice_control **Platforms**: Windows 11 **Device context**: Desktop

Built-in Windows 11 voice control that lets the user operate the entire OS and applications by
voice. Supports label-based commands ("click Submit"), number overlays (numbers appear on all
interactive elements), and grid navigation (screen divided into numbered grid squares). Also
supports dictation for text input, voice-driven scrolling ("scroll down"), and window management
("minimize window"). Uses on-device speech recognition. The user can chain commands and use
contextual phrases. Works with all Windows applications including web browsers, desktop apps, and
UWP apps. Interaction quality depends heavily on accessible names matching visible labels.

### macOS Voice Control

**Category**: voice_control **Platforms**: macOS **Device context**: Desktop

Built-in macOS voice control with similar capabilities to Windows Voice Access: label-based
commands, number overlays, and grid navigation. Also supports comprehensive dictation with
formatting commands ("new line", "cap that"), text editing ("select previous word", "delete that"),
and navigation ("scroll down", "go to top"). Uses on-device speech recognition. Can control all
macOS applications. Uniquely supports custom vocabulary and command creation for power users.

### iOS Voice Control

**Category**: voice_control **Platforms**: iOS, iPadOS **Device context**: Mobile

Built-in iOS/iPadOS voice control for touchscreen devices. The user speaks commands to tap elements
by their visible label, uses number overlays, or uses grid navigation. Supports dictation, text
editing, and gesture simulation ("swipe left", "long press"). On-device speech recognition. Touch
interactions are simulated through voice commands — the user says "tap Submit" instead of physically
tapping. Custom gestures that have no voice equivalent are a barrier.

### Android Voice Access

**Category**: voice_control **Platforms**: Android **Device context**: Mobile

Google's voice control app for Android. Displays numbered labels on all interactive elements, and
the user speaks the number or the visible label to interact. Supports dictation, scrolling, and
basic navigation commands. Less mature in label-matching than iOS or Windows — primarily
number-based interaction. The user often works through numbered overlays rather than natural
language commands. Custom gestures and complex interactions without voice alternatives are barriers.

## Exploration Strategies

### Speaking visible labels to activate controls

Test "click [label]" and "tap [label]" for visibly labeled buttons, links, and controls; label
activation is commonly the most efficient path when supported. Icons may suggest "Settings" for a
gear, "Search" for a magnifying glass, or "Menu" for a hamburger, but interpretation varies. A
"click Settings" command can fail against "Preferences" or "options-gear-icon"; missing tooltips or
accessible names can require number overlays.

**AT Mechanisms**: Voice command: "click [label]", "tap [label]" **Device context**: All

**UI Requirements**: Every interactive element must have a visible text label (or a visible tooltip
on hover/focus that voice control can read). The visible label must match the accessible name so the
word the user sees is the word they can say to activate the element. Icon-only buttons must have
accessible names that match the icon's commonly understood meaning. When visual labels are
abbreviated or use jargon, the accessible name should include the full, natural-language equivalent.

### Number overlay navigation

Test "show numbers" and spoken-number activation when labels are missing, ambiguous, or mismatched.
Number overlays provide a fallback but add commands and target-finding effort; dozens of controls
may clutter the overlay. Verify reliable exposure on the tested platform. Preference for labels or
numbers varies, so assess fallback burden rather than prescribing a universal preference.

**AT Mechanisms**: Voice command: "show numbers", then "[number]" **Device context**: All

**UI Requirements**: All interactive elements must be programmatically exposed (in the accessibility
tree) for number overlays to detect them. Custom interactive elements that are not in the
accessibility tree won't receive numbers. The number overlay should not obscure critical content.
Minimising the need for number overlays by providing clear visible labels is the primary goal.

### Grid navigation

Test "show grid" and repeated spoken grid numbers to narrow toward unlabeled, unnumbered, canvas, or
freeform targets. This last-resort path requires multiple commands per target and can be slow or
effortful. Evaluate the burden of routine grid navigation and availability of labeled alternatives.

**AT Mechanisms**: Voice command: "show grid", then "[grid number]", repeat to narrow **Device
context**: All

**UI Requirements**: Avoid designs that require grid navigation. Ensure all interactive elements are
in the accessibility tree with appropriate labels. Canvas-based interfaces, drawing tools, and
freeform interaction areas should provide a voice-operable alternative (e.g., a panel with labeled
controls for canvas operations).

### Dictation for text input

Test dictation as text input with formatting ("period", "new line", "cap") and editing ("select
previous word", "delete that", "correct [word]"). Command/dictation mode switching varies by
platform. Aggressive autocorrect, auto-advancing focus mid-sentence, and character limits that
truncate dictation can create barriers.

**AT Mechanisms**: Dictation mode, voice commands for text editing and formatting **Device
context**: All

**UI Requirements**: Text input fields should accept dictation gracefully. Autocorrect should be
configurable or overridable. Multi-step or multi-field forms should not auto-advance focus (the user
needs control over when to move to the next field). Character counters should be visible so the user
knows when they're approaching limits. Rich text editors should support dictation without formatting
conflicts.

### Avoiding accidental command activation during dictation

Voice platforms typically distinguish command mode (operating UI) and dictation mode (entering
text), but boundaries may be unclear. Test dictated text against page-wide single-character
shortcuts — '?' for help, '/' for search, 'b' for a sidebar. Transcribed letters can trigger
unintended commands; relying on constrained phrasing is not a dependable substitute for shortcut
controls.

**AT Mechanisms**: Dictation mode (transcribes speech into keystrokes), application keyboard
shortcuts **Device context**: All

**UI Requirements**: Page-wide single-character shortcuts can be turned off, remapped to require a
modifier, or scoped to a focused component. Otherwise dictation may trigger unintended commands and
repeated recovery. This shares the keyboard single-key-shortcut requirement; long, unpredictable
transcribed keystroke streams can increase exposure in dictation contexts.

### Voice-driven scrolling and navigation

Test "scroll down", "scroll up", "page down", "go back", and "click [navigation link]" without
manual scroll-wheel, touch-gesture, or keyboard fallback. Long pages lacking skip-to-content or
section navigation may require repeated commands. Include voice switching between applications,
window management, and system UI where relevant to the task.

**AT Mechanisms**: Voice commands: "scroll down/up", "page down/up", "go to top/bottom" **Device
context**: All

**UI Requirements**: Pages should not be excessively long — or should provide in-page navigation
(table of contents, skip links, section headings that can be targeted by label). Infinite scroll is
particularly problematic: the user must keep saying "scroll down" with no clear end. Paginated
content with labeled page controls is preferable. Scroll position should not reset after
interactions.

### Visual scanning and layout comprehension _(from shared)_

When visual scanning is available and preferred, page regions such as the header, navigation, main
content, sidebar, and footer can help establish layout. Visible control affordances and hierarchy
through headings, spacing, colour, and size may help locate actions. Do not assume that visual
scanning is available or that these cues work alone.

**AT Mechanisms**: Visual perception **Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive
elements must look interactive (visible borders, underlines, or other affordances). Primary actions
should be visually prominent.

### Reading and scrolling _(from shared)_

Visual reading may proceed sequentially or through heading scans, with scrolling to reach content
beyond the viewport. Evaluate logical flow appropriate to the writing system, such as top-to-bottom
and left-to-right in LTR content. Do not assume one reading direction or scrolling method across
languages and input configurations.

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture **Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line
spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages
should provide navigation aids (table of contents, back-to-top).

### Form interaction _(from shared)_

Form tasks may involve reaching fields, typing, selecting options, checking boxes, and submitting
through different input methods. Evaluate clear labels, placeholder text that does not replace
labels, and actionable error feedback without assuming pointer access.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels) **Device
context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly
indicated. Error messages must be specific, adjacent to the field, and visible without scrolling.
Successful submission must be clearly confirmed.

### Navigation and wayfinding _(from shared)_

Menus, breadcrumbs, links, and browser back/forward can support navigation between pages and views.
Evaluate whether the current location, available destinations, and return paths are understandable
through the access strategies in scope.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls **Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active
nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work
predictably.

## Interaction Contexts

### Voice-primary operation without manual input

Evaluate voice as the primary command channel with manual input unavailable. Relevant contexts may
include high-level spinal cord injury (quadriplegia/tetraplegia), severe motor disability, limb
absence, or neuromuscular condition; none determines an individual's input options. Voice experience
and efficient command patterns vary. Head- or eye-tracking may supplement voice for some
configurations, but cannot substitute for checking a voice-operable path when manual fallback is
excluded.

**Primary AT**: Windows Voice Access, macOS Voice Control, iOS Voice Control, Android Voice Access
**Device context**: All **Preferred navigation**: Speaking visible labels to activate controls,
Number overlay navigation, Voice-driven scrolling and navigation

**Expectations**:

- Every interactive element has a visible label that matches its accessible name
- No interaction requires manual input (drag-and-drop, click-and-hold, drawing) without a
  voice-operable alternative
- Icon-only controls have accessible names matching their visual meaning
- Text input fields accept dictation without interference (no aggressive autocorrect, no
  auto-advance)
- Hover-revealed controls have voice-accessible alternatives
- Pages provide efficient navigation (skip links, labeled sections) to reduce repeated scroll
  commands
- CAPTCHAs have a voice-compatible alternative
- No time-limited interactions that expire before voice commands can complete

### New / infrequent user _(from shared)_

First-time or infrequent interaction may require rediscovering controls and workflows. Labels,
accessible affordances, and progressive disclosure can support learning without requiring prior
knowledge of shortcuts or hidden features.

**Primary AT**: None **Device context**: All **Preferred navigation**: Visual scanning and layout
comprehension, Navigation and wayfinding, Form interaction

**Expectations**:

- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user _(from shared)_

Frequent interaction may build familiarity with layouts, shortcuts, and workflows. Consistency and
efficient paths can support established strategies; changes may require relearning. Expertise in a
task does not establish expertise with every assistive technology.

**Primary AT**: None **Device context**: All **Preferred navigation**: Mouse / pointer interaction,
Navigation and wayfinding

**Expectations**:

- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **Discovering speakable labels**: Evaluate first-visit label discovery, for example "click
  Settings" for a gear icon and "show numbers" if that command fails. Failure does not alone prove a
  naming mismatch; inspect the name and actual recognition result. Consistent, predictable naming
  can reduce the effort of learning working commands.

- **Number overlay vs. grid as fallback**: Familiarity and preference may affect use of labels,
  numbers, and grids. New users may use overlays broadly; experienced users may prefer efficient
  labels where reliable. Evaluate discovery of working label paths and fallback controls rather than
  prescribe a progression shared by everyone.

- **Dictation mode context switching**: Voice control platforms typically distinguish between
  command mode (voice commands operate UI) and dictation mode (voice input becomes text). The user
  must learn when each mode is active and how to switch. Some platforms auto-switch when focus
  enters a text field; others require an explicit command. Text fields that don't trigger the
  expected mode switch, or that capture voice commands as text, create confusion.

- **Managing voice fatigue**: Extended voice use may cause vocal fatigue. Evaluate efficient paths
  that minimize unnecessary commands, support label-based activation alongside overlays, and reduce
  excessive scrolling or multi-step workflows. Effort and preferred command patterns vary.

- **Hover-revealed content may be inaccessible**: Where the configured voice path does not provide
  hover, tooltips, expanded menus, controls, and preview panels revealed only on hover may remain
  unavailable. Test discoverable voice-operable focus- or click-triggered alternatives; do not infer
  that every voice platform or configuration lacks hover support.

- **First visit** _(from shared)_: Familiar web, desktop, and mobile conventions may support
  learning, but recognition of hamburger menus, search icons, tabs, or modals is not guaranteed.
  Explain unfamiliar patterns and expose their purpose through accessible labels and feedback.

- **Mental models** _(from shared)_: Early interactions may establish expectations. Inconsistent
  behavior, such as a button that sometimes navigates and sometimes submits, can undermine
  confidence and require additional checking.

- **Error recovery** _(from shared)_: Support recovery from mistakes through undo, appropriate
  confirmation dialogs, and clear error messages. Make the consequences of irreversible actions
  clear rather than assuming every mistake can be avoided.

- **Cognitive load** _(from shared)_: Clutter, excessive options, and unclear hierarchy can increase
  attention and memory demands. Evaluate those demands in the task context without inferring a
  person's cognitive capabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

After the user speaks a command, does the interface provide visible feedback that the command was
received and acted upon? Voice commands can fail silently — the user says "click Submit" and nothing
happens because the accessible name doesn't match. The system should visually confirm the result of
an action: focus movement to new content, a loading indicator, a success message. If nothing visible
changes after a voice command, the user cannot tell whether the command failed, was misrecognised,
or succeeded with no visible effect.

### Heuristic 2 — Match Between System and Real World

Visible labels must match the user's natural language expectation for the element. A gear icon
should have an accessible name like "Settings" — what the user would naturally call it — not an
internal identifier. The foundation is the match between what the user sees and what they can say:
the accessible name must contain the visible label text. For icon-only controls, the accessible name
should match the icon's commonly understood meaning. If the icon is ambiguous, a visible tooltip or
text label resolves the ambiguity for both the user's understanding and their ability to command the
element by voice.

### Heuristic 3 — User Control and Freedom

Can the user escape from modals, cancel operations, and undo actions by voice? "Click Close", "click
Cancel", "press Escape" must work. If a modal has no visible close button (only an X icon with no
accessible name), the user must use number overlays to close it. Drag-and-drop interfaces without a
voice-operable alternative (e.g., a "Move to..." menu) trap the user. After dismissing an overlay,
the interface should return to a state where the user's next voice command acts predictably.

### Heuristic 4 — Consistency and Standards

Consistent visible labels and accessible names across the interface let the user build a reliable
command vocabulary. If "Settings" works on one page but the same icon requires "Preferences" on
another, the user's learned commands break. Interactive elements should follow consistent labeling
patterns throughout the application. Custom widgets should follow standard interaction patterns that
voice control platforms can handle.

### Heuristic 5 — Error Prevention

Evaluate unintended commands, such as "click Submit" instead of "click Save", and speech-recognition
errors without ranking input methods or people as inherently less precise. Destructive actions
should require explicit confirmation; forms should not submit irreversibly on a single voice
command. Aggressive autocorrect that changes dictated text without consent can introduce errors.

### Heuristic 6 — Recognition Rather than Recall

Evaluate discoverable speakable labels that indicate control function. Hover-revealed,
scroll-revealed, or context-menu-only controls may require recalling their existence and a voice
path to them. Visibility alone does not guarantee command support; verify the accessible name and
operable reveal path.

### Heuristic 7 — Flexibility and Efficiency of Use

Evaluate the common command-cost hierarchy: label command > number overlay > grid navigation.
Overlays add a step and grids add multiple narrowing steps; preferred paths and performance vary.
Support clear label activation wherever possible, and measure fallback burden for unlabeled or
icon-only controls that may add task time or vocal fatigue.

### Heuristic 8 — Aesthetic and Minimalist Design

Evaluate overlay clutter and command ambiguity from many unlabeled or ambiguously labeled targets.
Fewer clearly labeled controls may reduce burden. An icon-only toolbar with 20+ icons and no labels
may require repeated overlays; test actual naming and command support rather than assume every
action needs fallback.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Test failure after "click Submit": is there useful feedback or only silence? Distinguish recognition
errors, naming mismatches, and non-interactive elements from evidence. The interface cannot
eliminate recognition errors, but matching visible labels and names can reduce application-caused
failures. Form correction should preserve dictated values and allow field-specific edits.

### Heuristic 10 — Help and Documentation

Is there documentation explaining which voice commands work with the interface? For complex
applications, a voice command reference or cheat sheet is valuable — the equivalent of keyboard
shortcuts documentation for keyboard users. Help content must itself be navigable by voice: labeled
links, scrollable by voice command, and with a discoverable entry point ("click Help").
Voice-operated interfaces benefit from tooltips or inline hints that show the speakable label for
ambiguous controls.
