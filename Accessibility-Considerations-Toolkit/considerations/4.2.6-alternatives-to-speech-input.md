# FPS 4.2.6 — Usage with no or limited vocal capability

Where ICT requires vocal input from users, the ICT provides at least one mode of operation that does
not require them to generate vocal output.

## Evaluation Considerations

Evaluate task completion when vocal input is unavailable, not attempted, or not reliably recognised.
Check voice commands, dictation, search, authentication, and phone/IVR spoken-response gates for
non-voice alternatives. This lens restricts reliance on voice input for evaluation only; it neither
impersonates a non-speaking person nor assumes visual, auditory, motor, or cognitive capabilities.

Also assess noisy environments where recognition fails, quiet settings where speech is
inappropriate, and public spaces where privacy rules out verbal interaction. These can create the
same voice-input dependency barrier without equating the broader experiences of situational
constraints and speech disabilities.

Check both absent vocal input and repeated recognition failure. Non-speaking access and speech a
particular system does not reliably recognise require equivalent alternatives, whether voice is
never attempted or attempts fail. Do not label speech or a person inherently unintelligible or infer
a diagnosis from recognition failure.

For each screenshot or interface, consider:

- Does ANY feature require voice input? Voice search, voice commands, voice-activated controls,
  dictation fields, voice CAPTCHA, voice biometric authentication?
- Is there ALWAYS a text, keyboard, or touch alternative to every voice-dependent feature?
- Are voice features presented as OPTIONAL enhancements or as the PRIMARY (or sole) interaction
  path?
- If a voice interaction fails or is not attempted, does the system offer a graceful FALLBACK to
  text input, or does it loop ("I didn't catch that, please try again")?
- For phone/IVR integrations: is there a text-based alternative channel (chat, web form, SMS) for
  completing the same task?
- For voice-based authentication or verification: can the user authenticate via an alternative
  method (password, biometric, security key)?

Possible barriers include voice-only CAPTCHA without text, voice biometrics without fallback, IVR
trees without keypad or text channels, dictation-only input, voice commands without keyboard
equivalents, and blocking "speak now" prompts without dismiss/skip.

Focus findings on required or strongly preferred voice paths without equivalent alternatives.
Keyboard, mouse, touch, or text alternatives must be verified in their own access contexts, not
presumed universally usable. Screenshots alone cannot establish workflow fallback or authentication
behaviour.

## Assistive Technologies

### Standard input (no voice)

**Category**: keyboard_mouse_touch **Platforms**: Windows, macOS, Linux, iOS, Android **Device
context**: All

Keyboard, mouse, and touchscreen are possible non-voice paths, not a declaration that every person
uses all three or needs no specialised AT. Check typing instead of dictation, click/tap instead of
voice commands, and text search instead of voice search. Chat, messaging, and web forms may replace
phone/voice tasks; each alternative needs equivalent functionality and suitable access.

## Exploration Strategies

### Seeking text alternatives to voice features

For voice search, dictation, commands, voice CAPTCHA, and authentication, check co-located non-voice
alternatives: keyboard-accessible search, text CAPTCHA, password/security key, or chat/web form
beside phone/IVR. Distinguish an audio CAPTCHA that requires listening from a voice CAPTCHA that
requires vocal output; this lens targets the latter requirement.

**AT Mechanisms**: Visual scanning, keyboard and mouse interaction **Device context**: All

**UI Requirements**: Every voice-dependent feature must have a visible, discoverable text or
keyboard alternative presented in the same context. The alternative must not be hidden behind
additional steps or buried in settings. Voice and text paths should be visually co-located so the
user immediately sees the non-voice option.

### Avoiding voice-gated workflows

Inspect account creation, verification, support, and task completion for speech gates. A voice-only
gate blocks completion under this lens; check non-voice authentication, text support, and
keyboard-operable alternatives throughout the workflow.

**AT Mechanisms**: Visual scanning, navigation through workflow steps **Device context**: All

**UI Requirements**: No critical workflow step should require voice as the sole input method.
Authentication, verification, and support must offer at least one non-voice path. If voice is
offered as an option within a workflow, the non-voice alternative must be equally prominent and
functional.

### Visual scanning and layout comprehension _(from shared)_

When visual scanning is available and preferred, page regions such as the header, navigation, main
content, sidebar, and footer can help establish layout. Visible control affordances and hierarchy
through headings, spacing, colour, and size may help locate actions. Do not assume that visual
scanning is available or that these cues work alone.

**AT Mechanisms**: Visual perception **Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive
elements must look interactive (visible borders, underlines, or other affordances). Primary actions
should be visually prominent.

### Mouse / pointer interaction _(from shared)_

Mouse, trackpad, or touch-pointer interaction may involve clicking, selecting text, dragging,
hovering for tooltips, or opening context menus. Evaluate the actions supported by the chosen input
method; hover and sustained dragging are not available in every pointer context.

**AT Mechanisms**: Mouse, Trackpad, Touchscreen **Device context**: Desktop

**UI Requirements**: Interactive elements are easy to activate with the intended pointer action and
are far enough apart that users do not accidentally activate adjacent controls. Hover states should
indicate interactivity. Drag-and-drop should have clear affordances.

### Reading and scrolling _(from shared)_

Visual reading may proceed sequentially or through heading scans, with scrolling to reach content
beyond the viewport. Evaluate logical flow appropriate to the writing system, such as top-to-bottom
and left-to-right in LTR content. Do not assume one reading direction or scrolling method across
languages and input configurations.

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture **Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line
spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages
should provide navigation aids (table of contents, back-to-top).

### Form interaction _(from shared)_

Form tasks may involve reaching fields, typing, selecting options, checking boxes, and submitting
through different input methods. Evaluate clear labels, placeholder text that does not replace
labels, and actionable error feedback without assuming pointer access.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels) **Device
context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly
indicated. Error messages must be specific, adjacent to the field, and visible without scrolling.
Successful submission must be clearly confirmed.

### Navigation and wayfinding _(from shared)_

Menus, breadcrumbs, links, and browser back/forward can support navigation between pages and views.
Evaluate whether the current location, available destinations, and return paths are understandable
through the access strategies in scope.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls **Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active
nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work
predictably.

### Touch / pointer interaction _(from shared)_

Touch interaction may include taps, swipes, pinch-zoom, or long presses, depending on the device and
access method. Direct touch has no hover preview; evaluate discoverable controls, target size, and
alternatives to complex gestures. Do not require every touch interaction pattern to be available to
the same person.

**AT Mechanisms**: Touchscreen tap, Swipe gestures, Pinch-zoom **Device context**: Mobile

**UI Requirements**: Touch targets are easy to activate without accidentally activating adjacent
controls — small or tightly packed targets force users to retry or hit the wrong control. No
reliance on hover for essential information. Custom gestures must have single-pointer alternatives.
Drag-and-drop must have tap-based alternatives. No accidental activation from scroll gestures.

## Interaction Contexts

### User who cannot use voice input

When voice is unavailable or repeatedly misrecognised, check visible text alternatives before any
attempt and immediate fallback after failure. Relevant contexts may include non-speaking from birth,
post-laryngectomy, motor speech disorders such as dysarthria, stuttering, or an accent poorly
supported by a recognition model; none predicts an individual's speech or preferred input. Noise,
quiet-space rules, and privacy may also rule out voice. A "please try again" loop without a
non-voice path can block the task.

**Primary AT**: Standard input (no voice) **Device context**: All **Preferred navigation**: Visual
scanning and layout comprehension, Mouse / pointer interaction, Form interaction

**Expectations**:

- Voice input is never required for any feature or workflow step
- Text alternatives exist for every voice-dependent feature
- Authentication and verification never require voice biometrics as the sole method
- Phone/IVR-based services have a text channel alternative (chat, web form, email)
- Voice recognition failure leads to a clear, immediate text-based fallback — the system does not
  loop endlessly on failed attempts
- Voice features are optional, not the default or sole path
- The user can disable or bypass voice features without losing functionality

### New / infrequent user _(from shared)_

First-time or infrequent interaction may require rediscovering controls and workflows. Labels,
accessible affordances, and progressive disclosure can support learning without requiring prior
knowledge of shortcuts or hidden features.

**Primary AT**: None **Device context**: All **Preferred navigation**: Visual scanning and layout
comprehension, Navigation and wayfinding, Form interaction

**Expectations**:

- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user _(from shared)_

Frequent interaction may build familiarity with layouts, shortcuts, and workflows. Consistency and
efficient paths can support established strategies; changes may require relearning. Expertise in a
task does not establish expertise with every assistive technology.

**Primary AT**: None **Device context**: All **Preferred navigation**: Mouse / pointer interaction,
Navigation and wayfinding

**Expectations**:

- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **Discovering voice requirements**: The user must be able to determine early whether an interface
  or workflow requires voice input. Interfaces should make this clear upfront — not after the user
  has invested effort in a multi-step workflow only to encounter a voice-gated step they cannot
  complete. Labels like "voice required" or visible text alternatives next to voice features help
  the user plan their approach.

- **Voice recognition failure recovery**: Check whether "Try typing instead" reveals a viable
  fallback after failed or skipped voice input. A repeated "I didn't catch that, try again" loop can
  conceal non-voice access and discourage further attempts; do not assume everyone will first try
  voice.

- **Phone/IVR alternative discovery**: Check text alternatives before entry to the phone tree. A
  voice menu that does not reveal chat or web forms can leave available non-voice routes
  undiscovered.

- **First visit** _(from shared)_: Familiar web, desktop, and mobile conventions may support
  learning, but recognition of hamburger menus, search icons, tabs, or modals is not guaranteed.
  Explain unfamiliar patterns and expose their purpose through accessible labels and feedback.

- **Mental models** _(from shared)_: Early interactions may establish expectations. Inconsistent
  behavior, such as a button that sometimes navigates and sometimes submits, can undermine
  confidence and require additional checking.

- **Error recovery** _(from shared)_: Support recovery from mistakes through undo, appropriate
  confirmation dialogs, and clear error messages. Make the consequences of irreversible actions
  clear rather than assuming every mistake can be avoided.

- **Cognitive load** _(from shared)_: Clutter, excessive options, and unclear hierarchy can increase
  attention and memory demands. Evaluate those demands in the task context without inferring a
  person's cognitive capabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

Check visible listening/expected-input status and a non-voice alternative. Failed or skipped
recognition must reveal a viable path rather than silently waiting or timing out; text acceptance
should be apparent before an attempt.

### Heuristic 2 — Match Between System and Real World

Check "Just say...", "Tell us...", and "Speak your answer" for implied voice dependence. Use
input-neutral wording such as "Enter your search" or "Provide your answer"; a sole microphone
affordance should not conceal available text input.

### Heuristic 3 — User Control and Freedom

Check dismissal or skipping of "Speak now" overlays and voice modals, and switching to text at any
workflow step without losing progress. A voice gate with no bypass blocks this lens, analogous to a
keyboard trap but not evidence of one.

### Heuristic 4 — Consistency and Standards

Are text alternatives consistently available wherever voice input is offered? If voice search has a
text search field but voice authentication has no password fallback, the inconsistency forces the
user to guess which voice features have alternatives and which do not. Every voice feature should
follow a consistent pattern: voice input is offered alongside a visible, equivalent text
alternative.

### Heuristic 5 — Error Prevention

Voice-only verification, vocal-response CAPTCHA, and voice biometrics without fallback block this
no-voice condition rather than merely increasing error risk. Check non-voice methods in
security-critical flows to prevent account lockout or abandonment; severity must reflect the
evidenced workflow consequence.

### Heuristic 6 — Recognition Rather than Recall

Text alternatives to voice features must be discoverable in context — visible alongside the voice
option, not hidden in settings, help pages, or separate workflows. If the user must remember that a
text alternative exists and navigate to a different location to access it, the design forces recall
rather than recognition. Voice and non-voice paths should be co-located and equally prominent.

### Heuristic 7 — Flexibility and Efficiency of Use

Check equivalent keyboard, mouse, touch, or text alternatives wherever voice is offered, without
requiring a single modality. Non-voice completion should not add unnecessary steps. Even if voice is
an efficient shortcut, text access must remain discoverable and efficient.

### Heuristic 8 — Aesthetic and Minimalist Design

Check whether voice prompts, "speak now" overlays, or microphone UI block interaction or conceal
usable text input. Present non-voice access as a primary option; the presence of optional voice UI
alone is not a barrier.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

After unavailable or unrecognised speech, check immediate text fallback without discarding prior
input. "I didn't catch that, please try again" without an alternative can be a dead-end loop. IVR
failure should offer a text channel or a human-assisted non-voice route, not restart the menu; a
human agent who still requires speech is not an equivalent fallback.

### Heuristic 10 — Help and Documentation

Is there documentation explaining how to use the interface without voice? For interfaces with
prominent voice features, help content should describe the text-based alternatives and how to access
them. Text-based support channels (chat, email, web form) must be available alongside phone support
— a "Contact us" page that lists only a phone number is a significant barrier. If the interface has
a voice-first onboarding flow, a text-based onboarding alternative must be equally accessible.
