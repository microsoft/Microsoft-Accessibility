# FPS 4.2.1 — Usage without vision

Where ICT provides visual modes of operation, the ICT provides at least one mode of operation that
does not require vision.

## Evaluation Considerations

Evaluate whether tasks can be completed without relying on visual output, using screen-reader speech
and/or a refreshable braille display. This lens sets nonvisual access conditions for evaluation; it
does not represent a blind person or establish anyone's other capabilities.

Nonvisual access often builds understanding **sequentially**, with structural navigation providing
an outline rather than a visual glance. Information must be available in a logical order through
speech and/or braille. Evaluate desktop keyboard navigation through a virtual representation
separately from mobile touch gestures, with no hover state or physical keyboard assumed in the
mobile context.

For each screenshot, consider:

- **DISCOVER**: How would the user find what is on this screen? Can they build a structural outline
  through headings, landmarks, and element lists? Does the tab order reveal controls in a logical
  sequence?
- **UNDERSTAND**: How would the user understand relationships conveyed visually — groupings,
  proximity, colour-coded states, iconography? These must be conveyed through accessible names,
  roles, and structure.
- **OPERATE**: How would the user interact with controls? On desktop: keyboard access, focus
  management, mode switching between reading and form interaction. On mobile: touch targets, swipe
  navigation, gesture alternatives.
- **KNOW**: How would the user know the result of their actions? Status changes, confirmations, and
  errors must be announced — not conveyed only through visual changes.
- **RECOVER**: What happens when things go wrong? Can the user dismiss overlays, undo actions, and
  re-orient after unexpected changes?

Possible nonvisual barriers include interactive elements that don't behave as expected, controls
whose names don't convey purpose, content that changes without announcement, missing keyboard
access, unlabelled images, complex forms, missing headings, excessive links, and complex data
tables. Screenshots can suggest checks but cannot establish accessibility-tree, announcement, or
keyboard behaviour without source or interaction evidence.

## Assistive Technologies

### JAWS

**Category**: screen_reader **Platforms**: Windows **Device context**: Desktop

Commercial screen reader by Freedom Scientific — the most-used desktop screen reader, dominant in
North America. JAWS builds a **virtual buffer** (virtual cursor) — a linear representation of the
interface constructed from the accessibility tree. The user navigates this buffer using keyboard
commands rather than interacting with the application directly.

**Cursor modes**: JAWS maintains separate cursors. The **PC Cursor** follows the system caret for
text editing and standard application interaction. The **Virtual PC Cursor** navigates the virtual
buffer for reading and structural navigation. The **JAWS Cursor** tracks the mouse pointer to reach
areas the other cursors cannot. Users toggle between these with Insert+Z.

**Browse vs. forms mode**: In browse mode, letter keys are intercepted as navigation shortcuts — H
jumps to headings, R to landmarks, T to tables, F to form fields, B to buttons, and so on. When
focus enters a form control, JAWS auto-switches to **forms mode**, passing keystrokes to the
application for typing and selection. Users exit forms mode to resume structural navigation. This
mode switching is invisible to the application but fundamentally changes the user's available
commands at any moment.

**Element navigation**: Single-letter shortcuts (with Shift for reverse) let the user jump between
element types. The **elements list** (Insert+F3) opens a dialog listing all elements of a chosen
type — links, headings, buttons, form fields — for rapid scanning without reading through content
sequentially.

**Table navigation**: Once inside a table, Ctrl+Alt+Arrow keys move between cells. The user can read
the current row, column, or cell in isolation. Column and row headers are announced with each cell
if properly associated.

### NVDA

**Category**: screen_reader **Platforms**: Windows **Device context**: Desktop

Free and open-source screen reader by NV Access — widely used globally, especially outside North
America. NVDA uses a modifier key (Insert by default, configurable to Caps Lock) for its commands.

**Browse vs. focus mode**: Like JAWS, NVDA operates in two modes. **Browse mode** intercepts
keystrokes for structural navigation — H for headings, D for landmarks, K for links, F for form
fields, B for buttons. **Focus mode** passes keystrokes to the application for form interaction.
Toggle manually with Insert+Space, or NVDA auto-switches when focus enters or leaves form controls.

**Element navigation**: Single-letter shortcuts mirror JAWS in concept but differ in some key
bindings (e.g., D for landmarks vs. R in JAWS; K for links vs. U in JAWS). The **Elements List**
(Insert+F7) provides a unified dialog to browse headings, links, form fields, and landmarks.

**Text reading granularity**: The user can read by line (arrow keys), word (Ctrl+Left/Right),
character (Left/Right), sentence (Alt+Up/Down), or paragraph (Ctrl+Up/Down). Continuous reading from
the current position (Insert+Down) is how users consume body text.

**Learning aids**: NVDA offers a keyboard help mode (Insert+1) that announces what each key does
without executing the action — useful for beginners learning navigation commands.

### VoiceOver (macOS)

**Category**: screen_reader **Platforms**: macOS **Device context**: Desktop

Built-in macOS screen reader. VoiceOver uses a **VO modifier** (Ctrl+Option) for all commands, which
can be locked (VO+;) to avoid holding both keys continuously.

**No modal navigation**: Unlike Windows screen readers, VoiceOver does not switch between browse and
focus modes. The **VoiceOver cursor** moves through elements and can interact with them directly —
VO+Space activates any element (links, buttons, checkboxes, etc.) without mode switching.

**The Rotor**: VoiceOver's primary discovery and navigation tool. VO+U opens the Rotor, which
displays categorised lists of interface elements — headings, links, form controls, landmarks,
tables, images. The user switches categories with Left/Right arrows, selects an element with
Up/Down, and jumps to it with Enter. The Rotor can be filtered by typing (e.g., "nav" to filter
landmarks). This is how VoiceOver users get the structural overview that Windows SR users get
through elements lists and single-letter shortcuts.

**Element-type navigation**: VO+Cmd+letter shortcuts jump to the next element of a type (H for
headings, L for links, J for form elements, T for tables, G for graphics). Add Shift to go to the
previous occurrence.

**Object interaction**: For complex controls and embedded content, VO+Shift+Down enters the object
(interacting with its children) and VO+Shift+Up exits back to the parent level.

### Narrator

**Category**: screen_reader **Platforms**: Windows **Device context**: Desktop

Built-in Windows screen reader. Uses a **scan mode** for structural navigation (similar to browse
mode in JAWS/NVDA) with the Narrator key (Caps Lock or Insert) as modifier. Frequently encountered
as a secondary or fallback screen reader on machines without JAWS/NVDA installed. Increasingly
capable but still has gaps for complex interactive interfaces compared to JAWS/NVDA.

### VoiceOver (iOS)

**Category**: screen_reader **Platforms**: iOS **Device context**: Mobile

Built-in iOS screen reader — the dominant mobile screen reader. Touch-based interaction: the user
drags a finger across the screen to hear elements under the touch point, or swipes right/left to
move through elements sequentially. Double-tap activates the focused element. The **rotor**
(two-finger twist gesture) provides quick navigation by headings, links, form controls, landmarks,
and other element types — functionally equivalent to the macOS Rotor but controlled by gesture. No
physical keyboard assumed — all interaction through touch gestures. Typing uses the on-screen
keyboard with touch-type or standard-typing mode.

### TalkBack

**Category**: screen_reader **Platforms**: Android **Device context**: Mobile

Built-in Android screen reader — predominantly used in regions where Android market share is higher.
Linear navigation model: swipe right/left to move through elements sequentially, double-tap to
activate. The **reading controls menu** (swipe up then right) provides navigation by headings,
links, and controls — functionally similar to VoiceOver's rotor but with different gestures.
Multi-finger gestures for scrolling (two-finger swipe) and global actions (two-finger tap for
pause).

### Refreshable braille display

**Category**: braille_display **Platforms**: Cross-platform, paired with screen reader

Braille output may be used alongside speech or independently. Displays one line of braille at a time
— common sizes are 40-cell (~40 characters) and 14-cell (portable, ~14 characters).
Character-by-character or word-by-word reading reveals exact spelling, punctuation, and formatting
that speech may gloss over. Routing buttons above each cell allow direct cursor placement. In a
braille-only context, including some Deaf-blind access contexts, all information must reach the
braille display without requiring speech or audio cues.

## Exploration Strategies

### Heading navigation

Check whether quick-nav keys and heading lists provide a structural outline without reading every
element. Heading navigation may be a primary strategy when its commands are familiar, or remain
undiscovered when they are not; experience alone does not establish a preferred method.

**AT Mechanisms**: H / Shift+H (JAWS, NVDA), VO+Cmd+H (VoiceOver macOS), Rotor > Headings (VoiceOver
iOS, TalkBack), Headings list (JAWS: Insert+F6, NVDA: Insert+F7, VoiceOver: Rotor) **Device
context**: All

**UI Requirements**: Properly nested heading hierarchy. Headings must be descriptive and reflect
content groupings. Every visually distinct section should have a heading. Skipped heading levels
create confusion about structure. One primary heading per page or view identifying the content.

### Find / search

Check keyword-based find when the desired text is known but its location is not. This bypasses
structure and can provide a fallback when structural shortcuts are unfamiliar or headings are
inadequate, without assuming a particular skill level.

**AT Mechanisms**: Ctrl+F (system find), NVDA+Ctrl+F (NVDA find), Ctrl+F (JAWS virtual find)
**Device context**: Desktop

**UI Requirements**: Content must be real text, not rendered in images or canvas elements. Search
results must be navigable and focus must move to matched content. Content that has not yet rendered
(lazy-loaded) will not be found.

### Landmark navigation

Check jumps between named regions (navigation, main content, complementary, footer) for nonvisual
orientation. Landmark navigation can supplement headings or serve as a primary path depending on
task, structure, and command familiarity.

**AT Mechanisms**: D / Shift+D (NVDA), R / Shift+R (JAWS), Rotor > Landmarks (VoiceOver) **Device
context**: All

**UI Requirements**: Distinct regions of the interface must be identifiable as landmarks. When
multiple landmarks of the same type exist, each should have a unique accessible name to distinguish
them. The main content area should be identifiable as the primary landmark.

### Tab-through interactive elements

Check Tab navigation between focusable links, buttons, and inputs: it reveals controls but skips
static content. It may be a primary path when other commands are unfamiliar. On mobile, swiping
right/left through all elements sequentially serves a similar discovery purpose but includes static
content.

**AT Mechanisms**: Tab / Shift+Tab (desktop), Swipe right / left (mobile), F key for form fields
(JAWS, NVDA) **Device context**: All

**UI Requirements**: Logical tab order matching visual flow. All interactive elements must be
focusable. Custom controls must be in the tab order with appropriate roles. Focus must be managed
correctly for dynamic content — when content appears, changes, or is dismissed, focus must move to
or return from the appropriate element.

### Screen reader elements list

Check a dialog or rotor listing links, headings, form fields, or landmarks for rapid discovery
without sequential reading. Names must convey purpose in isolation; repeated 'click here' and 'read
more' labels can make different actions indistinguishable.

**AT Mechanisms**: Insert+F7 (NVDA Elements List), Insert+F3 (JAWS), Rotor (VoiceOver — both desktop
and mobile) **Device context**: All

**UI Requirements**: Links and buttons must have descriptive accessible names that convey purpose
when read in isolation. Avoid duplicate names for elements with different destinations or actions.
Vague or redundant names make the elements list unusable.

### Sequential reading

Check linear reading from top to bottom using arrow keys (desktop) or sequential swipe gestures
(mobile), especially for body text, instructions, and unfamiliar content. Sequential reading can be
a fallback or primary strategy; it is not universal.

**AT Mechanisms**: Down / Up arrow (desktop browse mode), Swipe right / left (mobile sequential
navigation) **Device context**: All

**UI Requirements**: Reading order must reflect logical content order. Visual reordering that
diverges from the underlying content order creates a confusing, non-sequential experience. Content
should be meaningful when read linearly.

### Touch exploration

Check mobile touch-and-drag exploration for speech about elements under the touch point. It can
support spatial orientation and, on repeat visits, navigation by remembered approximate positions;
labels and discoverable targets must also support unfamiliar layouts.

**AT Mechanisms**: Touch-and-drag (VoiceOver, TalkBack), Double-tap to activate, Swipe gestures for
navigation, Rotor / reading controls for element-type navigation **Device context**: Mobile

**UI Requirements**: Touch targets must be large enough to discover via touch exploration. Elements
must be properly labelled. Custom gestures must have single-pointer alternatives. Drag-and-drop must
have accessible alternatives. No reliance on hover interactions.

### Form interaction _(from shared)_

Form tasks may involve reaching fields, typing, selecting options, checking boxes, and submitting
through different input methods. Evaluate clear labels, placeholder text that does not replace
labels, and actionable error feedback without assuming pointer access.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels) **Device
context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly
indicated. Error messages must be specific, adjacent to the field, and visible without scrolling.
Successful submission must be clearly confirmed.

### Navigation and wayfinding _(from shared)_

Menus, breadcrumbs, links, and browser back/forward can support navigation between pages and views.
Evaluate whether the current location, available destinations, and return paths are understandable
through the access strategies in scope.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls **Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active
nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work
predictably.

### Touch / pointer interaction _(from shared)_

Touch interaction may include taps, swipes, pinch-zoom, or long presses, depending on the device and
access method. Direct touch has no hover preview; evaluate discoverable controls, target size, and
alternatives to complex gestures. Do not require every touch interaction pattern to be available to
the same person.

**AT Mechanisms**: Touchscreen tap, Swipe gestures, Pinch-zoom **Device context**: Mobile

**UI Requirements**: Touch targets are easy to activate without accidentally activating adjacent
controls — small or tightly packed targets force users to retry or hit the wrong control. No
reliance on hover for essential information. Custom gestures must have single-pointer alternatives.
Drag-and-drop must have tap-based alternatives. No accidental activation from scroll gestures.

## Interaction Contexts

### Desktop screen reader user

When desktop navigation uses headings, landmarks, elements lists, and quick-nav keys, assess
efficient structure and standard keyboard patterns for tabs, menus, dialogs, and trees. Switching
between screen readers (e.g., JAWS at work, NVDA at home) makes consistency important. At a high
speech rate, redundant announcements can impede navigation; rates and strategies vary.

**Primary AT**: JAWS, NVDA, VoiceOver (macOS) **Device context**: Desktop **Preferred navigation**:
Heading navigation, Landmark navigation, Screen reader elements list

**Expectations**:

- Fast, efficient navigation through well-structured heading hierarchy
- Predictable, consistent interaction patterns across pages and across screen readers
- Minimal verbosity — no redundant role announcements, no excessive decorative content
- Keyboard shortcuts that don't conflict with screen reader commands
- Dynamic content announced appropriately, not intrusively

### Mobile screen reader user

When mobile access uses swipe gestures, rotor/reading controls, and touch exploration, assess a
coherent responsive layout rather than a shrunken desktop interface. No hover state or physical
keyboard is assumed in this context; desktop-first complexity can add unnecessary navigation.

**Primary AT**: VoiceOver (iOS), TalkBack **Device context**: Mobile **Preferred navigation**: Touch
exploration, Sequential reading, Heading navigation (via rotor)

**Expectations**:

- Touch targets large enough to discover via touch exploration
- Swipe navigation that follows a logical order
- No reliance on hover interactions
- Responsive layouts that don't break screen reader navigation on mobile viewports
- Custom gestures have single-pointer alternatives

### Beginner screen reader user

When screen-reader commands are unfamiliar, Tab and sequential reading may be the available paths,
with find as a fallback. This may occur after recent vision loss, with ageing, or when first
learning AT, but none establishes skill or speech-rate preference. Check simple structures, explicit
instructions, and orientation support, including at a lower speech rate.

**Primary AT**: NVDA, Narrator **Device context**: All **Preferred navigation**: Tab-through
interactive elements, Sequential reading, Find / search

**Expectations**:

- Simple, linear content flow that makes sense read top to bottom
- Clear labels and instructions before form fields, not after
- Obvious affordances — controls that announce what they do
- Error messages that explain what went wrong and what to do next
- Forgiving interactions — easy to undo, confirm before destructive actions

### Braille display user

When output is read character by character on a refreshable braille display, check exact spelling,
punctuation, and formatting that speech may gloss over. Evaluate braille alongside speech and
braille-only access separately; some Deaf-blind contexts require all information without audio.

**Primary AT**: Refreshable braille display paired with JAWS, NVDA, or VoiceOver **Device context**:
All **Preferred navigation**: Sequential reading, Heading navigation

**Expectations**:

- Clean text content without decorative Unicode characters or excessive emoji
- Proper use of punctuation and formatting — braille reveals every character
- Tables with proper header associations (braille reads cell by cell)
- All interactive feedback available as text (not only as audio cues)

### New / infrequent user _(from shared)_

First-time or infrequent interaction may require rediscovering controls and workflows. Labels,
accessible affordances, and progressive disclosure can support learning without requiring prior
knowledge of shortcuts or hidden features.

**Primary AT**: None **Device context**: All **Preferred navigation**: Visual scanning and layout
comprehension, Navigation and wayfinding, Form interaction

**Expectations**:

- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

## Learning Considerations

- **First visit**: Check orientation through headings and landmarks before a task, without assuming
  familiarity with either command set. Poor headings can hide the relevant section. Sequential
  discovery can require more navigation than a visual scan.

- **Habituating**: On repeat visits, check whether remembered locations and interactions remain
  reliable. A primary action that alternates between first and last in tab order can require
  relearning.

- **Mode switching** (desktop): Check browse versus forms/focus modes where supported, particularly
  in JAWS/NVDA; VoiceOver macOS does not use this modal model. Entering a field typically switches
  available commands automatically. Poor form structure can cause confusing switches or hide
  instructions between fields.

- **Recovery from disorientation**: Check reorientation after overlays, lost focus, or dynamic
  changes. Changes may remain unannounced unless explicitly communicated; unexpected controls and
  silent updates can conceal both result and recovery path.

- **Cognitive load of sequential access**: Building layout understanding piece by piece can add
  navigation and memory demands, even with familiar commands. Check whether simplicity and clear
  structure reduce those demands rather than attributing a cognitive capacity to a group.

- **Desktop vs. mobile mental model differences**: Check coherent access across mobile swipes/rotor
  and desktop keyboard/modes where applicable. Layout adaptations are acceptable; losing information
  or access at mobile viewports is not.

- **Multi-screen-reader context switching**: When access switches between screen readers with
  different bindings and behaviours, check standard semantics and platform conventions rather than
  depending on a workaround for one product.

- **First visit** _(from shared)_: Familiar web, desktop, and mobile conventions may support
  learning, but recognition of hamburger menus, search icons, tabs, or modals is not guaranteed.
  Explain unfamiliar patterns and expose their purpose through accessible labels and feedback.

- **Mental models** _(from shared)_: Early interactions may establish expectations. Inconsistent
  behavior, such as a button that sometimes navigates and sometimes submits, can undermine
  confidence and require additional checking.

- **Error recovery** _(from shared)_: Support recovery from mistakes through undo, appropriate
  confirmation dialogs, and clear error messages. Make the consequences of irreversible actions
  clear rather than assuming every mistake can be avoided.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

System status must be available through screen-reader speech and/or braille; visual-only colour
changes, progress bars, and spinners do not satisfy this lens. Check programmatic updates or
appropriate focus movement after actions. Silent dynamic changes can leave their result
undiscovered, while rapid sequential announcements can interrupt one another and lose information.

### Heuristic 2 — Match Between System and Real World

Language and metaphors must make sense without a visual referent. Icon-only controls are meaningless
without accessible names. All interactive elements need descriptive names that convey purpose out of
context (they appear in elements lists in isolation). Spatial language ('click the button on the
right', 'see the sidebar') should be supplemented with structural references.

### Heuristic 3 — User Control and Freedom

Check nonvisual overlay dismissal, undo, and back navigation. Return focus to the trigger after
dismissal. Vision-only authentication blocks this lens; destructive confirmations need appropriate
focus management, and mobile overlays must support the standard dismiss gesture.

### Heuristic 4 — Consistency and Standards

Check consistent headings, landmarks, and standard keyboard patterns for tabs, menus, dialogs, and
trees. Changing a tab panel from arrows to Tab across pages can invalidate a learned pattern. Verify
standard semantics and platform controls across screen readers rather than assuming consistency.

### Heuristic 5 — Error Prevention

Nonvisual recovery can require re-reading forms, re-navigating to fields, and re-attempting input.
Reduce that cost with clear constraints, format hints, and required-field indicators before input.
Required indicators must be programmatically associated with the field, not only visual. Destructive
confirmations must be announced and focusable.

### Heuristic 6 — Recognition Rather than Recall

Check programmatic association of labels, instructions, and context without relying on visual
proximity. Breadcrumbs, titles, and region labels should support nonvisual orientation. Form labels
must persist rather than disappear like placeholder text.

### Heuristic 7 — Flexibility and Efficiency of Use

Check efficient nonvisual paths through headings, landmarks, shortcuts, and web skip links, without
requiring familiarity with every strategy. Support multiple paths simultaneously. The mobile rotor
provides element-type navigation; long Tab or swipe sequences to primary content can remain a
barrier.

### Heuristic 8 — Aesthetic and Minimalist Design

Check whether redundant roles, announced decoration, verbose status, or excessive links add
listening, braille reading, or swiping time. Streamline navigation and names and hide purely
decorative content from assistive technology, while preserving information needed for the task.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Check actionable errors associated with fields and available through screen-reader speech and/or
braille. Summaries should navigate to fields, and inline validation should expose errors as they
occur. What failed, where, and how to fix it must be understandable sequentially, without visual
scanning.

### Heuristic 10 — Help and Documentation

Help content must be accessible to screen readers — no text in images, proper heading structure,
navigable contents. Complex workflows need orientation cues (step indicators, progress
announcements). Search is a critical navigation fallback for users who cannot visually scan. On
mobile, help should be reachable without complex gesture sequences.
