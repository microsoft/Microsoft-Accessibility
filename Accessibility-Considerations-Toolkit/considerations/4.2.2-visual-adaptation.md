# FPS 4.2.2 — Usage with limited vision

Where ICT provides visual modes of operation, the ICT provides features enabling users with limited
vision to make better use of their limited vision.

## Evaluation Considerations

Evaluate whether size, contrast, and layout adapt when default presentation makes text or fine
details difficult to perceive. Assess enlargement, magnification, contrast settings, and combined
visual/speech access without impersonating a person with limited vision or assuming their colour
perception or other capabilities.

Evaluate EACH of these access contexts; they may overlap and do not define fixed user types:

1. Moderate zoom (OS scaling + browser zoom up to ~200%) with text reflow and platform-level
   enlargement
2. Screen magnification (ZoomText, Windows Magnifier, macOS Zoom at 3×–8×), where a small viewport
   requires panning to read and navigate
3. Windows High Contrast Mode or forced-colours themes for contrast-related barriers, with or
   without magnification
4. Dual-channel access combining screen magnification with a screen reader, switching between visual
   scanning and speech output

For each screenshot, consider:

- Does text WRAP TO FIT each in-scope scrolling container? When the containers the user reads in
  have content areas around 320 CSS pixels wide, can each line be read by scrolling along the
  line-progression axis (vertically for top-to-bottom scripts) without also having to scroll across
  the line to finish it? Are there containers where lines extend past the container's content area
  and force the user to scroll horizontally?
- At HIGH MAGNIFICATION (3×–8×), is the layout predictable enough to build a spatial mental model?
  Are related elements spatially co-located? Is content left-justified for efficient vertical
  panning?
- Do HOVER TOOLTIPS and popups remain stable when the user pans the magnified viewport? Do they
  disappear when the mouse moves slightly?
- Does FOCUS MOVEMENT behave predictably? Does focus jump to unexpected locations (disorienting) or
  fail to move to dynamically appearing content like modals and error messages (content lost
  off-screen)?
- In HIGH CONTRAST / FORCED-COLOURS mode, do all elements remain visible and distinguishable? Are
  focus indicators, borders, and state changes preserved? Do icons and images have sufficient
  contrast or fallbacks?
- Are VISUAL LANDMARKS (dividers, section boundaries, headings) clear enough to aid orientation
  within a magnified viewport?
- Are VISUAL INDICATORS (borders, focus rings, selection states) thick and high-contrast enough to
  be distinguishable at high magnification?
- Do DRAG-AND-DROP interactions have keyboard alternatives? Dragging is extremely difficult at high
  magnification.
- For the DUAL-CHANNEL user: is all visual content accessible to a screen reader? Do magnifier
  viewport and screen reader focus stay synchronised? Does the accessibility tree remain correct at
  all zoom levels?
- Does the interface provide AUDIO FEEDBACK (earcons, sounds) to supplement visual cues that may be
  off-screen or hard to locate?
- Are DROP-DOWNS, SELECT LISTS, and AUTOCOMPLETE suggestions scaling with the increased text size,
  or stuck at default size?

The evaluation concerns efficient reading, orientation within a constrained viewport, and adaptation
to display settings without losing information or functionality. Magnification level and contrast
needs vary independently; do not infer a person's vision from settings or assume magnification meets
every access need.

IMPORTANT — Assessing perceivability at high magnification:

Whether an element is perceivable depends on a COMBINATION of visual attributes, not any single
attribute in isolation. Research on visual perception of controls shows that identifiability comes
from multiple inner attributes of a component (font weight, fill, stroke, elevation, size,
iconography, semantic familiarity) and outer attributes of its context (spacing, layout, position,
alignment, adjacent elements, expectation given context). It is the combination of these attributes
that aids identification.

When assessing whether a UI element is perceivable at high magnification:

- Consider all the inner and outer attributes together, not any single attribute (e.g., a small
  icon) in isolation.
- An element's position relative to the scanning path matters: left-aligned elements may be in the
  primary path when panning left-to-right. Do not flag left alignment alone as hard to discover;
  establish the relevant path and context.
- If the combination of attributes (position, text label, icon, spacing, contextual expectations)
  makes the element identifiable, do not flag it as a visibility concern based on a single attribute
  being small.

## Assistive Technologies

### OS text size / DPI scaling

**Category**: display-scaling **Platforms**: Windows, macOS, Linux **Device context**: Desktop

User increases the operating system's text size, DPI scaling, or display resolution to enlarge all
system UI and application content proportionally. On Windows this is Settings > Display > Scale; on
macOS it is System Settings > Displays > resolution / text size. Applications that honour platform
scaling conventions enlarge alongside the OS. Those that do not may render at default size within a
scaled environment, creating inconsistent experiences.

### Browser zoom

**Category**: zoom **Platforms**: Windows, macOS, Linux **Device context**: All

User zooms the browser viewport via Ctrl/Cmd + Plus (or mouse wheel). At 200% zoom on a 1280px
browser, the effective viewport is 640px. Browser zoom triggers the same responsive layout
adjustments that occur when the browser window is resized — lines of text re-wrap to fit the
narrower effective viewport. This is the user's primary path to reading content at a comfortable
text size while still scrolling in only one direction.

### ZoomText

**Category**: screen-magnifier **Platforms**: Windows **Device context**: Desktop

Dedicated screen magnification software that enlarges a portion of the rendered display at 1×–60×.
The magnified viewport pans with the mouse cursor or keyboard focus. ZoomText provides smoothing,
colour enhancement, cursor/focus enhancements, and optional built-in speech output. Unlike browser
zoom, ZoomText does NOT trigger content reflow — it magnifies the already-rendered layout, so lines
of text that exceed the magnified viewport width require horizontal panning to read.

### Windows Magnifier

**Category**: screen-magnifier **Platforms**: Windows **Device context**: Desktop

Built-in Windows magnification tool (Settings > Accessibility > Magnifier). Offers full-screen,
lens, and docked modes. Tracks mouse cursor, keyboard focus, and text insertion point. Lower feature
set than ZoomText but available on every Windows machine at no additional cost. Like ZoomText, does
not trigger content reflow.

### macOS Zoom

**Category**: screen-magnifier **Platforms**: macOS **Device context**: Desktop

Built-in macOS magnification (System Settings > Accessibility > Zoom). Supports full-screen,
split-screen, and picture-in-picture modes. Tracks keyboard focus and pointer. Can be toggled with
keyboard shortcut (Option+Cmd+8). Does not trigger content reflow.

### Windows High Contrast Mode

**Category**: forced-colours **Platforms**: Windows **Device context**: Desktop

Replaces application colours with a high-contrast system palette. Custom backgrounds, soft shadows,
and gradients disappear; only system colours and elements drawn as a visible outline survive. The
user selects a theme (e.g., High Contrast Black, High Contrast White) that determines the palette.
This is independent of magnification — some users use it alone, others combine it with a magnifier.

### Fusion (ZoomText + JAWS)

**Category**: combined **Platforms**: Windows **Device context**: Desktop

Bundles ZoomText screen magnification with JAWS screen reader in a single product. The user switches
fluidly between visual magnification and speech output. Magnified viewport tracks both mouse
position and screen reader focus. Common usage: magnification for layout orientation and spatial
context, speech for reading long text passages or navigating complex structures.

## Exploration Strategies

### Zoomed reading and text reflow

Evaluate reading at an enlarged text size without horizontal motion to finish a line. Keep needed
panes and views available, then assess window and divider resizing so each scrolling container
holding wrappable text has a content area around 320 CSS pixels wide. With correspondingly high
screen magnification, one such container fills the magnifier viewport. Check reading by scrolling
the container and panning along the line-progression axis (vertically, for top-to-bottom scripts),
without cross-line motion.

This requirement applies to screen magnification, browser zoom, and OS scaling. Browser zoom
automatically narrows responsive containers' effective width and triggers reflow. Screen
magnification does not trigger reflow itself, so check that scrolling containers wrap to their
available content width — down to around 320 CSS pixels. Two-dimensional content — data tables,
charts, interactive maps, persistent toolbars — is excepted and may scroll in both directions; this
exception does not imply a personal preference. Every other in-scope container and text sub-section
inside an excepted layout must support completing a line without horizontal motion.

To assess this interface requirement, apply this framework:

1. IDENTIFY CONTAINERS: Start top-level and get more granular. Identify each scrolling container,
   including containers that should scroll but do not, and containers whose contents may expand or
   whose size may shrink to the point that scrolling would be needed. Each scrolling container is
   independently in scope — the frame of reference for the rest of this framework is the container's
   own content area, not the application window or screen.

2. IDENTIFY CONTENT IN SCOPE: Within each container, identify linearly laid-out content where
   reducing the container's content width would cause lines to wrap — content where the user reads
   from one line to the next.

3. CHECK FOR FAILURE (all must be true for a failure):
   - Reading a line of in-scope text within the container would require scrolling or panning across
     the line to finish it, when the container's content area is narrow (around 320 CSS pixels
     wide).
   - The content is NOT two-dimensional layout content (data tables, charts, interactive maps,
     toolbars that must remain persistent).
   - No alternative path provides the same information and functionality in a layout that does wrap
     text to fit a narrow container.

4. IDENTIFY EXCEPTIONS: Data tables, charts, interactive visualisations, presentations, and
   interfaces requiring persistent toolbars are exempt from the wrap-to-fit requirement — but
   individual cells within tables, and text sub-sections within excepted layouts (dialogs, panels,
   descriptive text areas), must still wrap to fit narrow content widths.

5. CONSIDER CONTENT ADAPTATION: Content is allowed and expected to adapt or relocate at narrower
   container widths. Features hidden behind a menu, moved to a different view, or collapsed into an
   accordion are not failures here as long as they remain reachable. The question is whether
   information or functionality is lost — not whether the layout changes.

6. NOTE RELATED USER NEEDS: Problems that surface during zoomed reading often reflect adjacent user
   needs rather than wrap-to-fit failures — text that does not enlarge at all (text resize), layout
   that locks to one orientation when the user reorients to read, the focused control hidden behind
   a sticky header or non-modal overlay (focus not obscured), or no visible focus indicator at all
   (visible focus).

**AT Mechanisms**: Browser zoom (Ctrl/Cmd + Plus), OS DPI scaling, Screen magnifier with
user-resized container widths **Device context**: All

**UI Requirements**: Each in-scope scrolling container — every container holding linearly-laid-out
wrappable content — wraps its content to fit the container's own content area, including at narrow
widths around 320 CSS pixels. The user can read any line by scrolling the container along the
line-progression axis (vertically for top-to-bottom scripts) without scrolling or panning across the
line to complete it. Text must not clip, overlap, or be truncated when enlarged. Two-dimensional
content (data tables, charts, persistent toolbars) is excepted but should expose visible scroll
affordances when it overflows. Content that relocates or collapses at narrower container widths is
acceptable as long as the information and functionality remain reachable.

### Magnified viewport panning

At 3×–8× dedicated screen magnification, check orientation through a small portion of the layout.
Evaluate pointer movement, keyboard shortcuts (e.g., Alt+Ctrl+Arrow in Windows Magnifier), and
focus/cursor tracking. Systematic left-to-right, then downward panning is one possible path, not a
universal reading pattern.

**AT Mechanisms**: Mouse movement / trackpad, Magnifier keyboard shortcuts, Focus/cursor tracking
**Device context**: Desktop

**UI Requirements**: Predictable, consistent layout so the user can build a spatial mental model.
Left-justified content so vertical panning reveals sequential elements. Hover tooltips and popups
must remain stable during panning. Focus changes must not jump the viewport to an unexpected
location.

### Focus and cursor tracking

Check screen-magnifier tracking of keyboard focus and text cursor while navigating with Tab and
arrow keys. Automatic panning should keep the focused element visible; a focus move without viewport
tracking can require a manual search and disrupt orientation.

**AT Mechanisms**: Magnifier focus tracking, Keyboard navigation **Device context**: Desktop

**UI Requirements**: Focus must move to dynamically appearing content (modals, error messages, new
sections) so the magnifier can track it. Focus must not move without a corresponding user action.
Programmatic focus changes must land on the relevant element, not a distant container.

### High contrast scanning

With forced-colours or a high-contrast theme active, check content, system-foreground text,
interactive borders and outlines, and visual landmarks such as dividers and section boundaries.
System colours replace custom styling; missing boundaries can remove navigation cues.

**AT Mechanisms**: Windows High Contrast Mode, macOS Increase Contrast **Device context**: Desktop

**UI Requirements**: UI elements must remain visible and distinguishable in forced-colours mode.
Focus indicators must be drawn in a way that survives the theme — a visible outline survives,
decorative shadows or background fills do not. Images and icons must either have sufficient inherent
contrast or have a fallback that remains visible when custom colours are stripped.

### Dual-channel reading (magnification + speech)

When magnification and screen-reader speech are combined, check transitions from visual orientation
to headings, landmarks, or Tab navigation for reading or reaching sections. Speech should confirm
the displayed state and provide text access when visual reading requires excessive panning.

**AT Mechanisms**: Screen magnifier (visual), Screen reader (speech), Heading / landmark navigation
**Device context**: Desktop

**UI Requirements**: Magnified viewport and screen reader focus must remain synchronized. All
visually displayed content must be accessible to the screen reader. Screen reader announcements must
accurately reflect the visual state. Content that adapts at different zoom levels must maintain a
correct accessibility tree.

### Visual scanning and layout comprehension _(from shared)_

When visual scanning is available and preferred, page regions such as the header, navigation, main
content, sidebar, and footer can help establish layout. Visible control affordances and hierarchy
through headings, spacing, colour, and size may help locate actions. Do not assume that visual
scanning is available or that these cues work alone.

**AT Mechanisms**: Visual perception **Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive
elements must look interactive (visible borders, underlines, or other affordances). Primary actions
should be visually prominent.

### Mouse / pointer interaction _(from shared)_

Mouse, trackpad, or touch-pointer interaction may involve clicking, selecting text, dragging,
hovering for tooltips, or opening context menus. Evaluate the actions supported by the chosen input
method; hover and sustained dragging are not available in every pointer context.

**AT Mechanisms**: Mouse, Trackpad, Touchscreen **Device context**: Desktop

**UI Requirements**: Interactive elements are easy to activate with the intended pointer action and
are far enough apart that users do not accidentally activate adjacent controls. Hover states should
indicate interactivity. Drag-and-drop should have clear affordances.

### Reading and scrolling _(from shared)_

Visual reading may proceed sequentially or through heading scans, with scrolling to reach content
beyond the viewport. Evaluate logical flow appropriate to the writing system, such as top-to-bottom
and left-to-right in LTR content. Do not assume one reading direction or scrolling method across
languages and input configurations.

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture **Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line
spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages
should provide navigation aids (table of contents, back-to-top).

### Form interaction _(from shared)_

Form tasks may involve reaching fields, typing, selecting options, checking boxes, and submitting
through different input methods. Evaluate clear labels, placeholder text that does not replace
labels, and actionable error feedback without assuming pointer access.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels) **Device
context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly
indicated. Error messages must be specific, adjacent to the field, and visible without scrolling.
Successful submission must be clearly confirmed.

### Navigation and wayfinding _(from shared)_

Menus, breadcrumbs, links, and browser back/forward can support navigation between pages and views.
Evaluate whether the current location, available destinations, and return paths are understandable
through the access strategies in scope.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls **Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active
nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work
predictably.

### Touch / pointer interaction _(from shared)_

Touch interaction may include taps, swipes, pinch-zoom, or long presses, depending on the device and
access method. Direct touch has no hover preview; evaluate discoverable controls, target size, and
alternatives to complex gestures. Do not require every touch interaction pattern to be available to
the same person.

**AT Mechanisms**: Touchscreen tap, Swipe gestures, Pinch-zoom **Device context**: Mobile

**UI Requirements**: Touch targets are easy to activate without accidentally activating adjacent
controls — small or tightly packed targets force users to retry or hit the wrong control. No
reliance on hover for essential information. Custom gestures must have single-pointer alternatives.
Drag-and-drop must have tap-based alternatives. No accidental activation from scroll gestures.

## Interaction Contexts

### User with increased text size and moderate zoom

When platform-level enlargement is used without a dedicated magnifier, check OS text size/DPI
scaling, browser zoom up to approximately 200%, and available app-level font sizing. This may be
relevant with acuity around 20/70–20/200, but acuity does not determine settings. Dark mode or extra
contrast may also be used; assess forced-colours separately rather than assuming it is unnecessary.

**Primary AT**: OS text size / DPI scaling, Browser zoom **Device context**: Desktop **Preferred
navigation**: Zoomed reading and text reflow, Visual scanning and layout comprehension

**Expectations**:

- Text reflows without horizontal scrolling at up to 200% browser zoom — lines of text in in-scope
  containers fit within the effective viewport width
- Content that relocates or collapses at narrower viewports (e.g., menus behind hamburger icons)
  remains discoverable and reachable
- Drop-down menus, select lists, tooltips, and autocomplete suggestions scale with the increased
  text size — not stuck at default size
- Persistent UI elements (sidebars, toolbars) that reduce available content width still leave enough
  room for the content area to be readable
- No clipping, overlap, or truncation of enlarged text
- Simple, uncluttered layouts that reduce visual noise and support efficient scanning
- Consistent, predictable layout and navigation across views
- Clear, easy-to-distinguish iconography with text labels or accessible tooltips

### Screen magnifier user

When ZoomText, Windows Magnifier, or macOS Zoom is used at 300–500% or higher, check orientation and
panning through a small viewport. Acuity around 20/200–20/800 or higher, or visual field loss, may
be relevant contexts, not predictors of magnifier use. Magnification enlarges rendered layout
without reflow; browser zoom may be combined to trigger reflow first.

**Primary AT**: ZoomText, Windows Magnifier, macOS Zoom **Device context**: Desktop **Preferred
navigation**: Magnified viewport panning, Focus and cursor tracking

**Expectations**:

- Left-justified content so the user can pan straight down to find subsequent elements
- Hover and mouseover popups and tooltips remain visible and stable while the user pans within the
  magnified viewport — not disappearing when the mouse moves slightly
- Focus changes do not jump the magnified viewport to an unexpected screen location
- Dynamically appearing content (toasts, validation messages, modals, autocomplete) appears near the
  triggering element — not in a distant corner requiring extensive panning to locate
- Clear visual landmarks (bold dividers, section boundaries, styled headings) and visible
  connections between related areas and controls aid orientation within the narrow magnified
  viewport
- Visual indicators (borders, focus highlights, selection states) are clearly distinguishable at
  high magnification — subtle 1px borders or low-contrast highlights may be invisible
- Clear visual connections between stacked surfaces — modals, overlays, and dropdowns have an
  obvious visual relationship to their trigger
- Drag-and-drop interactions have keyboard or alternative non-drag mechanisms — dragging is
  extremely difficult at high magnification
- Audio or earcon feedback to confirm success, failure, or state changes supplements visual cues
  that may be off-screen or hard to locate
- Minimal wasted empty space (large margins, centred narrow content columns) that increases panning
  distance without adding value
- Consistent, predictable layout supports spatial memory across visits; clutter detracts from it
- Resizable content containers (draggable handles, collapsible panels) help reduce panning by
  narrowing content width

### User with contrast sensitivity relying on high contrast themes

When distinguishing foreground and background is difficult, assess Windows High Contrast Mode
(forced-colours), macOS Increase Contrast, or inverted colours as applicable. Contrast sensitivity
loss or photophobia may be relevant, with or without magnification and independently of acuity.
Specifically test whether the UI survives forced-colours overrides; these settings are not
interchangeable.

**Primary AT**: Windows High Contrast Mode **Device context**: Desktop **Preferred navigation**:
High contrast scanning, Visual scanning and layout comprehension

**Expectations**:

- All UI elements remain visible and distinguishable in forced-colours mode — focus indicators drawn
  as a visible outline survive the theme; indicators drawn only with decorative shadows or
  background fills disappear
- Visual indicators (borders, focus highlights, selection states, active/inactive states) remain
  clearly distinguishable — forced-colours can reduce all custom styling to a limited system
  palette, making previously distinct states look identical
- Meaning is not conveyed solely through subtle colour or background changes that forced-colours
  removes
- Images, icons, and SVGs have sufficient inherent contrast or a fallback that remains visible when
  custom colours are stripped; icon-only controls need text augmentation via labels or tooltips
- Visual landmarks — bold dividers, clear section boundaries, styled headings — survive
  forced-colours and continue to aid orientation
- Interactive element boundaries remain clearly differentiated from non-interactive content
- Visual connections between related controls and between stacked surfaces remain visible in
  forced-colours mode

### Low-vision user combining magnification with screen reader

When magnification supports overview and a screen reader supports reading or navigation, test
combinations such as Fusion (ZoomText + JAWS), Windows Magnifier with NVDA, and macOS Zoom with
VoiceOver. Check switching to speech for long passages, fatigue, pixelated or unreadable content,
and elements outside the current magnified view but reachable through screen-reader navigation.

**Primary AT**: Fusion (ZoomText + JAWS), Windows Magnifier **Device context**: Desktop **Preferred
navigation**: Dual-channel reading (magnification + speech), Focus and cursor tracking, Magnified
viewport panning

**Expectations**:

- Magnified viewport and screen reader focus remain synchronised — focus movement scrolls or pans
  the magnified view to the focused element
- All visually displayed content is accessible to the screen reader — no visual-only text in images
  or canvas elements
- Screen reader announcements accurately reflect what the user sees magnified — no mismatches
  between visual and programmatic state
- Audio or earcon feedback supplements visual cues for success, failure, and state changes — the
  dual-channel user may be looking at one area while the screen reader announces events from another
- Content that relocates, collapses, or hides at narrow or zoomed viewports retains proper
  accessibility tree structure so the screen reader can navigate to it even when visually hidden
- Screen reader serves as a fallback when visual magnification fails (pixelated rendering, vanishing
  hover popups, elements off-screen) — the interface must remain functionally complete via screen
  reader
- Drag-and-drop operations that are impractical visually at high magnification have
  screen-reader-accessible alternatives
- The interface works well in both modalities simultaneously — not just visually passable but
  semantically correct

### New / infrequent user _(from shared)_

First-time or infrequent interaction may require rediscovering controls and workflows. Labels,
accessible affordances, and progressive disclosure can support learning without requiring prior
knowledge of shortcuts or hidden features.

**Primary AT**: None **Device context**: All **Preferred navigation**: Visual scanning and layout
comprehension, Navigation and wayfinding, Form interaction

**Expectations**:

- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user _(from shared)_

Frequent interaction may build familiarity with layouts, shortcuts, and workflows. Consistency and
efficient paths can support established strategies; changes may require relearning. Expertise in a
task does not establish expertise with every assistive technology.

**Primary AT**: None **Device context**: All **Preferred navigation**: Mouse / pointer interaction,
Navigation and wayfinding

**Expectations**:

- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **First visit**: Check discoverable adaptation to magnification and contrast settings: reflow,
  preserved affordances, and reliable focus tracking. Failure to expose this behaviour can require
  trial-and-error at each zoom level.

- **Spatial memory is essential**: A small magnified viewport can make remembered positions useful
  for locating regions and controls. Consistent layout supports this strategy across visits; changes
  can add relearning and panning, without assuming everyone uses a spatial map.

- **Wayfinding within a magnified viewport**: Check bold dividers, boundaries, and consistent
  heading styles for distinguishing small panned views. Missing landmarks can make orientation
  difficult; reduce clutter without removing those cues.

- **Panning cost is cumulative**: Every unit of unnecessary horizontal space, every tooltip that
  vanishes on mouse movement, every focus jump to an unexpected location adds physical and cognitive
  effort. This accumulates across a session. Efficient layouts that minimise panning distance help
  users complete tasks before fatigue sets in.

- **Dual-channel switching**: Check transitions between magnification for orientation and speech for
  dense text, pixelated content, unstable popups, or off-screen elements. Each modality must remain
  supported; one may provide a fallback but cannot establish that a failure in the other (e.g., a
  broken accessibility tree) is resolved.

- **Common contrast minimums are not usability targets**: A contrast ratio just above 4.5:1 (for
  normal text) or 3:1 (for large text) is the typical conformance floor — calibrated roughly to
  20/40 vision — but remains difficult for many low-vision users, especially those with contrast
  sensitivity loss. Aim well above the minimum — ratios closer to 7:1 for body text (calibrated to
  roughly 20/80 vision) provide meaningfully better readability. Treat the typical conformance ratio
  as a floor, not a goal.

- **Evaluate text across all input states**: Placeholder text, user-typed text, selected text,
  disabled text, and error-state text can each have different contrast characteristics. A
  placeholder may pass contrast requirements while the typed text uses the same or a similarly
  low-contrast colour, making the input difficult to read once the user starts typing. Assess every
  text state, not just the empty or default state.

- **Dynamic content and magnifier spatial awareness**: In a magnified viewport, the user sees only a
  small area centred on the cursor or focus position. When new content appears dynamically
  (notifications, chat responses, live updates, toasts, validation messages), its distance from the
  tracked position determines whether the user notices it. Content that renders near the cursor is
  visible; content that appears far from the tracked position may go entirely unnoticed. Evaluate
  where new dynamic content renders relative to where the magnifier viewport is likely to be, and
  whether there is any signal (focus movement, auditory cue) to alert the user.

- **First visit** _(from shared)_: Familiar web, desktop, and mobile conventions may support
  learning, but recognition of hamburger menus, search icons, tabs, or modals is not guaranteed.
  Explain unfamiliar patterns and expose their purpose through accessible labels and feedback.

- **Mental models** _(from shared)_: Early interactions may establish expectations. Inconsistent
  behavior, such as a button that sometimes navigates and sometimes submits, can undermine
  confidence and require additional checking.

- **Error recovery** _(from shared)_: Support recovery from mistakes through undo, appropriate
  confirmation dialogs, and clear error messages. Make the consequences of irreversible actions
  clear rather than assuming every mistake can be avoided.

- **Cognitive load** _(from shared)_: Clutter, excessive options, and unclear hierarchy can increase
  attention and memory demands. Evaluate those demands in the task context without inferring a
  person's cognitive capabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

System status feedback must be perceivable within the magnified viewport. Loading indicators,
progress changes, and action confirmations that appear far from the user's current focus or viewport
position may never be seen. Consider: after the user activates a control, does the feedback appear
near the control? Can the magnifier's focus tracking bring the user to the feedback? Is there audio
confirmation (earcon) for users who may miss visual cues? In forced-colours mode, do status
indicators (progress bars, spinners) remain visible when custom colours are stripped?

### Heuristic 2 — Match Between System and Real World

Check metaphors that require full-page spatial relationships: they may fail within a small magnified
viewport. Icon controls need labels or stable, readable, unclipped tooltips. Forced-colours can
remove meaning from colour-dependent icons.

### Heuristic 3 — User Control and Freedom

Check accidental activation during magnified panning: a slight pointer movement can select an
unintended element. Keep undo, cancel, and escape routes locatable from the current viewport rather
than a distant corner. Modals and dialogs must support Escape dismissal; return focus to the trigger
so tracking restores orientation.

### Heuristic 4 — Consistency and Standards

Check consistent navigation placement and focus styling across pages, components, and zoom levels.
Moving navigation from left to top can add spatial remapping; changed indicators can hinder
recognition. System colours and outlines should preserve those patterns in forced-colours.

### Heuristic 5 — Error Prevention

Error prevention is critical because errors are expensive to recover from at high magnification —
finding the error message, locating the offending field, and fixing it all require panning. Provide
clear constraints and format hints before input. Required fields must be indicated in a way that
survives forced-colours (not just a coloured asterisk whose colour is stripped). Confirmation
dialogs for destructive actions must appear near the trigger, be fully visible within a magnified
viewport, and have clearly distinguishable confirm/cancel buttons.

### Heuristic 6 — Recognition Rather than Recall

A small viewport can separate sidebar context from main content. Persistent labels, section
headings, and breadcrumbs reduce repeated panning to recover context. Check bold dividers and
distinct section styling for orientation, including in forced-colours, where custom-background
landmarks may disappear while borders and text remain.

### Heuristic 7 — Flexibility and Efficiency of Use

Efficiency for magnifier users centres on reducing panning. Skip links, keyboard shortcuts, and
efficient tab order let the user jump directly to content instead of panning across the full layout.
Left-justified content allows efficient vertical panning. Resizable containers (collapsible
sidebars, adjustable panel widths) let the user optimise the layout for their magnification level.
For the dual-channel user, heading and landmark navigation via screen reader provides an alternative
to visual searching.

### Heuristic 8 — Aesthetic and Minimalist Design

At high magnification, clutter costs panning distance. Every decorative element, large margin, and
unnecessary whitespace between content forces the user to pan further. But stripping too much
removes the visual landmarks that aid orientation. The balance is: simple, clean layouts with clear
visual structure. In forced-colours mode, minimalist designs that removed visible borders in favour
of subtle background shading may lose all visual structure. Sufficient visual boundaries must
survive forced-colours.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Error messages must appear near the field that caused the error — a summary at the top of a long
form is invisible to a magnifier user currently viewing fields at the bottom. Inline validation
errors must be visually adjacent to their field and visible within the magnified viewport without
additional panning. In forced-colours mode, error states that rely on a red border or red text lose
their colour — they need an icon, text prefix ('Error:'), or outline change that survives. For
dual-channel users, errors must also be programmatically associated with the field so the screen
reader announces them when the field receives focus.

### Heuristic 10 — Help and Documentation

Help content and tooltips must be usable at high magnification. Tooltips triggered on hover must
remain visible while the user pans to read them — tooltips that vanish on slight mouse movement are
a major pain point for magnifier users. Tooltips must be large enough to read at the user's
magnification level and not clipped by viewport edges. Keyboard-triggered tooltips (on focus) should
also work. In forced-colours mode, tooltip styling (backgrounds, borders) must remain visible. Help
documentation should describe magnification and contrast features available in the product.
