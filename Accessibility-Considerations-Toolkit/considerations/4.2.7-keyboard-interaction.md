# FPS 4.2.7 — Usage with limited manipulation or strength

Where ICT requires manual actions, the ICT provides features that enable users to make use of the
ICT through alternative actions not requiring manipulation, pinching, or twisting of the wrist, or
simultaneous actions.

Evaluate possible barriers to **keyboard** operation where manipulation or strength requirements
make other input paths unavailable or unsuitable. For **pointing-device** contexts (touchscreen,
trackball, head pointer, eye-gaze, switch-driven pointer, or a mounted device) — including target
size and spacing, single-pointer operation without complex gestures or dragging, recovery from
accidental activation, and independence from device motion or a fixed orientation — see the
companion consideration (4.2.8-pointer-interaction.md, alias: pointer-interaction). Its software
lens is also relevant to 4.2.7, but does not establish compliance with 4.2.8's physical reach
requirement. For evaluation without keyboard or manual pointer input, see the companion
consideration (4.2.7-voice-control.md, alias: voice-control).

## Evaluation Considerations

Evaluate keyboard reachability, operability, visible focus, and keystroke efficiency. Test paths
without mouse, trackpad, or touchscreen input; these are evaluation boundaries, not claims about
anyone's overall abilities. Visual focus is examined here where it is used, without assuming clear
vision, layout comprehension, or the absence of other access requirements.

Consider EACH of these interaction contexts:

1. Slower typing and occasional miskeys with limited fine motor control — tremor may result in
   repeated or adjacent keypresses
2. One-handed or sequential keyboard input where simultaneous key combinations are unavailable
   without support

For each screenshot, consider:

- Can the user REACH every interactive element via Tab/Shift+Tab? Are there any elements that appear
  clickable but might not be keyboard focusable?
- Is the FOCUS INDICATOR clearly visible at all times? Can the user always tell which element is
  currently active?
- Do custom widgets (dropdowns, toggles, tabs, sliders, date pickers) support expected KEYBOARD
  PATTERNS (arrow keys, Enter, Space, Escape)?
- Are there any KEYBOARD TRAPS where the user could get stuck (e.g., a modal with no Escape support,
  a widget that captures Tab)?
- How many TAB STOPS does it take to reach the primary action? Are there skip links to bypass
  repetitive navigation?
- Are there any interactions that require MOUSE-SPECIFIC actions (hover to reveal, drag-and-drop,
  right-click context menus, click-and-hold) without keyboard alternatives?
- Do any interactions require SIMULTANEOUS KEY PRESSES that would be difficult for one-handed users?
- Are there TIME-LIMITED interactions (auto-closing notifications, session timeouts, disappearing
  tooltips) that disadvantage slow typists?
- What happens on ACCIDENTAL ACTIVATION? Are destructive actions reversible or confirmed before
  execution?

Use observed interface behavior and keyboard testing to assess these requirements; screenshots
cannot establish focusability, traps, or shortcut support. Do not infer a person's disability,
visual comprehension, or other capabilities from keyboard use.

## Assistive Technologies

### Standard keyboard (no mouse)

**Category**: keyboard **Platforms**: Windows, macOS, Linux **Device context**: Desktop

Keyboard-only operation uses Tab/Shift+Tab between interactive elements, Enter or Space to activate
buttons and links, arrow keys within composite widgets (tabs, menus, radio groups, dropdowns), and
Escape to close modals and menus. Evaluate these patterns without requiring mouse, trackpad, or
touchscreen fallback. Visible focus is an access requirement where visual tracking is used, not
evidence that all visual information is available.

## Exploration Strategies

### Tab-through interactive elements

Test Tab forward and Shift+Tab backward through focusable elements, a primary navigation method for
simple web pages and form regions. Compare discoverable interactive controls with keyboard-reachable
controls; visual prominence alone does not establish keyboard access.

In **rich interaction interfaces** — desktop applications, complex web applications (e.g., Outlook
on the web, Word Web, VS Code, Google Docs), and productivity tools — Tab navigates within the
current content region, while **pane/region navigation (F6, Ctrl+F6) and application keyboard
shortcuts are the primary methods** for moving between major areas. Tab alone may intentionally not
reach every area. Evaluate whether the application's region and shortcut model is available,
discoverable, and learnable, rather than assuming prior knowledge.

**AT Mechanisms**: Tab, Shift+Tab **Device context**: Desktop

**UI Requirements**: Logical, predictable tab order matching visual flow within each content region.
Every interactive element must be keyboard focusable. Focus indicator must be clearly visible so the
user can track where they are. In simple web pages, skip links help bypass repetitive navigation
blocks. In rich interaction interfaces, region navigation (F6) and documented keyboard shortcuts
serve the same purpose.

### Focus indicator tracking

Where keyboard operation uses visual focus tracking, invisible, dim, or lost focus can make the next
keypress's target unclear. Test focus after interactions and behind sticky headers, footers,
banners, and non-modal overlays. Screen-reader use and visual focus tracking can coexist; neither
establishes a person's visual capability.

**AT Mechanisms**: Visible focus ring / outline **Device context**: Desktop

**UI Requirements**: The focus indicator is always visible and distinguishable — large enough and
contrasting strongly enough against its surroundings that the user can spot it without effort.
Custom-styled focus indicators must not be less visible than the browser default, and must never be
suppressed without a clearly-visible replacement.

### Focused element remains visible

Test whether focus moves into content partly or fully covered by a sticky header, cookie banner,
non-modal overlay, or floating action panel. Obscured controls can prevent visual confirmation of
where a keystroke will act, even when keyboard focus itself remains present.

**AT Mechanisms**: Visible focus ring / outline, page scroll behaviour **Device context**: Desktop

**UI Requirements**: When a control receives focus, the user can see at least part of it. Sticky
headers, footers, banners, and non-modal overlays must not entirely hide the focused element. Scroll
behaviour must bring newly-focused content into the visible area, accounting for any fixed-position
chrome.

### Arrow key navigation within widgets

Test standard arrow-key movement between options in composite widgets — tab panels, dropdown menus,
radio groups, date pickers, and sliders. Missing expected keyboard patterns can make options
unreachable or create traps; do not assume every person already knows the patterns.

**AT Mechanisms**: Arrow keys (Up/Down/Left/Right), Home, End **Device context**: Desktop

**UI Requirements**: Custom composite widgets must implement standard keyboard patterns: arrow keys
to navigate options, Enter/Space to select, Escape to close. The widget manages focus internally so
the user moves between its options with arrow keys without tabbing out of the widget.

### Keyboard shortcuts and access keys

Evaluate shortcuts as optional paths that can reduce repetitive navigation. Access keys (Alt+key on
Windows, Ctrl+Option+key on macOS) jump directly to labeled elements. Application-defined shortcuts
(? for help, / for search) can speed up common tasks, depending on familiarity and input
configuration.

**AT Mechanisms**: Access keys, Application-defined shortcuts **Device context**: Desktop

**UI Requirements**: Shortcuts must not conflict with browser or OS shortcuts. Shortcuts must be
discoverable (documented in help). Single-character shortcuts can be turned off, remapped to require
a modifier, or scoped only to a component that has focus — a stray keystroke must not jump the user
out of their current flow. Shortcut combinations that require simultaneous key presses disadvantage
users with limited dexterity.

### Application-specific keyboard shortcuts

Many applications define keyboard shortcuts beyond browser/OS conventions. In **rich interaction
interfaces** (desktop applications, complex web applications, productivity tools), these shortcuts
are the **primary navigation and command model**, not merely supplementary accelerators. Evaluate
learning support and everyday operability without assuming familiarity or uniform learning
capability.

These may be documented in a help page, keyboard shortcuts dialog, or external documentation. When
evaluating, the evaluator should request any available keyboard shortcut documentation for the
product under test, whether provided as a link or pasted text. This documentation helps assess
whether shortcuts are available, discoverable, usable without a mouse, and free from conflicts. When
evaluating, also check whether the application offers a keyboard shortcuts help dialog (e.g.,
triggered by Shift+? or accessible via a Help menu). If shortcuts for the task under test are
documented there and the dialog is keyboard-accessible, shortcut discoverability is adequately
addressed.

**AT Mechanisms**: Application-defined shortcut keys, Help menu / keyboard shortcuts dialog **Device
context**: Desktop

**UI Requirements**: Application shortcuts should be documented and discoverable within the product
(e.g., a '?' help overlay listing shortcuts). Shortcuts should be learnable (consistent mnemonic
patterns). If the application has a shortcuts help dialog, it must itself be keyboard-accessible.

### Page structure scanning (visual)

Where visual scanning identifies a target through headings, groupings, whitespace, icons, or color,
test the keyboard path to it. Long tab sequences to visually prominent controls deep in DOM order
can add effort. Target discovery and target reachability are separate requirements and either may
present barriers.

**AT Mechanisms**: Visual scanning + Tab/shortcut to reach target **Device context**: Desktop

**UI Requirements**: Important actions should be reachable within a reasonable number of Tab stops.
Skip links, landmark shortcuts, and logical DOM order reduce unnecessary tabbing. Frequently used
controls should not be buried at the end of the tab order.

### Visual scanning and layout comprehension _(from shared)_

When visual scanning is available and preferred, page regions such as the header, navigation, main
content, sidebar, and footer can help establish layout. Visible control affordances and hierarchy
through headings, spacing, colour, and size may help locate actions. Do not assume that visual
scanning is available or that these cues work alone.

**AT Mechanisms**: Visual perception **Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive
elements must look interactive (visible borders, underlines, or other affordances). Primary actions
should be visually prominent.

### Reading and scrolling _(from shared)_

Visual reading may proceed sequentially or through heading scans, with scrolling to reach content
beyond the viewport. Evaluate logical flow appropriate to the writing system, such as top-to-bottom
and left-to-right in LTR content. Do not assume one reading direction or scrolling method across
languages and input configurations.

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture **Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line
spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages
should provide navigation aids (table of contents, back-to-top).

### Form interaction _(from shared)_

Form tasks may involve reaching fields, typing, selecting options, checking boxes, and submitting
through different input methods. Evaluate clear labels, placeholder text that does not replace
labels, and actionable error feedback without assuming pointer access.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels) **Device
context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly
indicated. Error messages must be specific, adjacent to the field, and visible without scrolling.
Successful submission must be clearly confirmed.

### Navigation and wayfinding _(from shared)_

Menus, breadcrumbs, links, and browser back/forward can support navigation between pages and views.
Evaluate whether the current location, available destinations, and return paths are understandable
through the access strategies in scope.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls **Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active
nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work
predictably.

### Touch / pointer interaction _(from shared)_

Touch interaction may include taps, swipes, pinch-zoom, or long presses, depending on the device and
access method. Direct touch has no hover preview; evaluate discoverable controls, target size, and
alternatives to complex gestures. Do not require every touch interaction pattern to be available to
the same person.

**AT Mechanisms**: Touchscreen tap, Swipe gestures, Pinch-zoom **Device context**: Mobile

**UI Requirements**: Touch targets are easy to activate without accidentally activating adjacent
controls — small or tightly packed targets force users to retry or hit the wrong control. No
reliance on hover for essential information. Custom gestures must have single-pointer alternatives.
Drag-and-drop must have tap-based alternatives. No accidental activation from scroll gestures.

## Interaction Contexts

### Slower or imprecise keyboard input

Evaluate slower standard-keyboard input, miskeys, and repeated or adjacent keypresses that may occur
with tremor. Mouse use may be painful or unavailable in contexts including cerebral palsy, muscular
dystrophy, repetitive strain injury, Parkinson's, or essential tremor, but diagnosis does not
determine an input pattern. Check confirmation dialogs, undo, and tolerance for imprecise input.

**Primary AT**: Standard keyboard (no mouse) **Device context**: Desktop **Preferred navigation**:
Tab-through interactive elements, Focus indicator tracking, Arrow key navigation within widgets

**Expectations**:

- Every interactive element is reachable and operable via keyboard
- Focus indicator is always clearly visible
- No keyboard traps — Escape always provides a way out
- No irreversible actions on single keypress without confirmation
- Debounce or tolerance for repeated/bounced key presses
- Clear undo mechanism for accidental actions
- Reasonable time limits or the ability to extend/disable them

### One-handed or sequential keyboard input

Evaluate one-handed keyboard input and sequential keypress paths. Limb difference, hemiplegia,
injury, or temporary impairment may be relevant contexts, without determining individual capability.
Where simultaneous combinations (Ctrl+Shift+T) are unavailable, check Sticky Keys or similar OS
support and alternatives that do not require simultaneous input.

**Primary AT**: Standard keyboard (no mouse) **Device context**: Desktop **Preferred navigation**:
Tab-through interactive elements, Keyboard shortcuts and access keys

**Expectations**:

- Critical actions don't require simultaneous modifier keys
- Sticky Keys compatibility — modifier state should not cause issues
- Shortcut keys that work with one hand on either side of keyboard
- Tab navigation that doesn't require excessive keypresses to reach targets
- No reliance on drag-and-drop or click-and-drag without keyboard alternative

### New / infrequent user _(from shared)_

First-time or infrequent interaction may require rediscovering controls and workflows. Labels,
accessible affordances, and progressive disclosure can support learning without requiring prior
knowledge of shortcuts or hidden features.

**Primary AT**: None **Device context**: All **Preferred navigation**: Visual scanning and layout
comprehension, Navigation and wayfinding, Form interaction

**Expectations**:

- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user _(from shared)_

Frequent interaction may build familiarity with layouts, shortcuts, and workflows. Consistency and
efficient paths can support established strategies; changes may require relearning. Expertise in a
task does not establish expertise with every assistive technology.

**Primary AT**: None **Device context**: All **Preferred navigation**: Mouse / pointer interaction,
Navigation and wayfinding

**Expectations**:

- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **First visit**: Evaluate discovery of keyboard patterns without assuming visual comprehension. On
  simple pages, test tab order, expected widget keys, and skip links. In rich interfaces (desktop
  apps, complex web apps, productivity tools), test region navigation (F6) and a keyboard shortcuts
  dialog (Shift+?, Help menu). Clear keyboard flow can reduce trial and error.

- **Rich interaction interfaces have a shortcut-first model**: In desktop applications and complex
  web applications, keyboard shortcuts and region navigation (F6, Ctrl+F6) are the primary way users
  move between major areas. Users learn this model through documentation, keyboard shortcuts
  dialogs, and exploration — once learned, it becomes the efficient everyday path. Tab is used
  within content regions, not across the entire interface. Evaluators should assess whether the
  shortcut model is documented and discoverable, not whether Tab alone can reach all areas.

- **Efficiency matters alongside discovery**: Even when content has been identified, reaching and
  operating it may require substantial effort. Unnecessary Tab stops, missing skip links, and
  keyboard traps can add physical effort and fatigue. Screen-reader and visual discovery
  requirements may also apply; neither is excluded by this lens.

- **Keystroke economy**: Keypress cost varies with input method, strength, and fatigue. A workflow
  requiring 30 Tab presses to reach the primary action may cause pain or exhaustion. Evaluate ways
  to minimize the keystroke cost of common tasks.

- **Error recovery is critical**: Tremor or limited control may increase accidental activation.
  Irreversible delete, submit, or navigate-away actions can carry substantial risk. Evaluate
  keyboard-accessible confirmation dialogs and undo as recovery paths.

- **Fatigue across sessions**: Motor fatigue may vary and worsen over time. A page manageable
  initially may become difficult after 20 minutes of keyboard-only use; this is an illustrative
  context, not a universal threshold. Evaluate efficient paths and support for breaks and
  resumption.

- **Hover-revealed information must also appear on keyboard focus**: Tooltips, labels, expanded
  controls, and any other information shown on mouse hover must also appear when the element
  receives keyboard focus. Hover-only information is invisible to keyboard users. This applies to
  icon-only buttons with hover tooltips, controls that expand on hover, and any progressive
  disclosure triggered by pointer interaction.

- **First visit** _(from shared)_: Familiar web, desktop, and mobile conventions may support
  learning, but recognition of hamburger menus, search icons, tabs, or modals is not guaranteed.
  Explain unfamiliar patterns and expose their purpose through accessible labels and feedback.

- **Mental models** _(from shared)_: Early interactions may establish expectations. Inconsistent
  behavior, such as a button that sometimes navigates and sometimes submits, can undermine
  confidence and require additional checking.

- **Error recovery** _(from shared)_: Support recovery from mistakes through undo, appropriate
  confirmation dialogs, and clear error messages. Make the consequences of irreversible actions
  clear rather than assuming every mistake can be avoided.

- **Cognitive load** _(from shared)_: Clutter, excessive options, and unclear hierarchy can increase
  attention and memory demands. Evaluate those demands in the task context without inferring a
  person's cognitive capabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

Evaluate visible feedback for keyboard paths: predictable focus after actions, loading states, and
confirmation that a keypress had an effect. Subtle changes, such as a distant color shift, may be
missed. After Enter activates a button, does focus move appropriately to relevant content, and is
progress clear? Consider additional feedback requirements without assuming vision is unrestricted.

### Heuristic 2 — Match Between System and Real World

For keyboard-only users: interactive elements should look and behave like their standard
counterparts. A custom widget styled as a button should respond to Enter and Space. A custom
dropdown should respond to arrow keys. If the visual appearance suggests one interaction model but
the keyboard behavior follows another, the user's expectations are violated. Icon-only controls
without visible text labels force the user to guess meaning.

### Heuristic 3 — User Control and Freedom

Keyboard users must be able to escape modals (Escape key), cancel operations (Cancel/Close buttons
in tab order), and undo actions. Focus traps without an exit leave the user stranded. After
dismissing an overlay, focus must return to the triggering element. Multi-step processes need a
keyboard-accessible way to go back. Consider: if the user accidentally triggers something, can they
get out using only the keyboard?

### Heuristic 4 — Consistency and Standards

Keyboard interaction patterns should be consistent across the interface. If Tab moves between items
in one list and arrow keys in another, the user must relearn navigation on every component. Follow
the standard keyboard interaction patterns users expect for composite widgets (tabs, menus,
comboboxes, dialogs, trees). Maintain consistent focus indicator styling across pages.

### Heuristic 5 — Error Prevention

Provide clear constraints and instructions before input, not just after errors. Confirmation dialogs
for destructive actions must be keyboard accessible. Required fields must be visually indicated.
Consider: a keyboard-only user filling out a form — can they understand the expected format before
making a mistake? Does pressing Enter in a text field accidentally submit the form?

### Heuristic 6 — Recognition Rather than Recall

Keyboard users benefit from persistent visible labels, clear page structure, and logical grouping.
Hidden navigation (hamburger menus) forces recall of how to access features. Labels on form fields
must persist (not disappear as placeholder text). Skip links and landmarks help users orient within
the page without scanning visually.

### Heuristic 7 — Flexibility and Efficiency of Use

Provide multiple navigation strategies: skip links, keyboard shortcuts, and efficient tab order.
Shortcuts should not conflict with browser or OS shortcuts. Documented shortcuts can reduce tab
count where they are usable and familiar. A page with 30 tab stops to the primary action may add
physical fatigue; minimize keystroke cost without assuming a uniform effort budget.

### Heuristic 8 — Aesthetic and Minimalist Design

For keyboard users, clutter means unnecessary tab stops. Every focusable decorative element, every
ad iframe in the tab order, every redundant link adds physical effort. Remove non-essential elements
from the tab order. Keep the path from page load to primary action as short as possible. Consider:
how many tab presses does the common task require?

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Error messages must be visually associated with their inputs and focus must move to the error or
errored field when errors appear. The user must be able to see which field has the error and
understand what to fix. Inline validation errors that appear dynamically must be near the field and
visible without scrolling. Error summary at the top of a form should be focusable.

### Heuristic 10 — Help and Documentation

Help content and documentation must be keyboard accessible. Tooltips triggered only on hover are
invisible to keyboard users — they need to appear on focus as well. Keyboard shortcut documentation
(e.g., a ? help dialog) should itself be keyboard-navigable and dismissible with Escape. Complex
custom widgets benefit from visible instructions describing their keyboard interaction patterns.

When an application provides a discoverable keyboard shortcuts dialog or help page that documents
relevant shortcuts, this **mitigates discoverability concerns** for those shortcuts. Before flagging
a keyboard shortcut as undiscoverable, check whether the application offers a shortcuts help
mechanism (e.g., Shift+?, a Help menu entry, or user documentation). If the shortcut is documented
there and the help is keyboard-accessible, discoverability is adequately addressed. If no such
mechanism exists, shortcut discoverability is a legitimate concern.
