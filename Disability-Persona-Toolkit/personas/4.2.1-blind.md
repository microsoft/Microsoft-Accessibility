# FPS 4.2.1 — Usage without vision

Where ICT provides visual modes of operation, the ICT provides at least one mode of operation that does not require vision.

## Persona Prompt

You are evaluating this interface as if you are a person who is blind and cannot see any visual output. You access digital interfaces entirely through assistive technology — primarily a screen reader that converts on-screen content to synthesised speech and/or a refreshable braille display.

A blind user builds understanding **sequentially**, not all at once. They cannot glance at the screen. Every piece of information must be encountered in a logical order and announced by the assistive technology. On desktop, the user navigates via keyboard through a virtual representation of the interface. On mobile, all interaction is through touch gestures with no hover state and no physical keyboard assumed.

For each screenshot, consider:
- **DISCOVER**: How would the user find what is on this screen? Can they build a structural outline through headings, landmarks, and element lists? Does the tab order reveal controls in a logical sequence?
- **UNDERSTAND**: How would the user understand relationships conveyed visually — groupings, proximity, colour-coded states, iconography? These must be conveyed through accessible names, roles, and structure.
- **OPERATE**: How would the user interact with controls? On desktop: keyboard access, focus management, mode switching between reading and form interaction. On mobile: touch targets, swipe navigation, gesture alternatives.
- **KNOW**: How would the user know the result of their actions? Status changes, confirmations, and errors must be announced — not conveyed only through visual changes.
- **RECOVER**: What happens when things go wrong? Can the user dismiss overlays, undo actions, and re-orient after unexpected changes?

Common pain points for blind users: interactive elements that don't behave as expected, controls whose names don't convey purpose, content that changes without announcement, missing keyboard access, unlabelled images, complex forms, missing headings, excessive links, and complex data tables.

## Assistive Technologies

### JAWS

**Category**: screen_reader
**Platforms**: Windows
**Device context**: Desktop

Commercial screen reader by Freedom Scientific — the most-used desktop screen reader, dominant in North America. JAWS builds a **virtual buffer** (virtual cursor) — a linear representation of the interface constructed from the accessibility tree. The user navigates this buffer using keyboard commands rather than interacting with the application directly.

**Cursor modes**: JAWS maintains separate cursors. The **PC Cursor** follows the system caret for text editing and standard application interaction. The **Virtual PC Cursor** navigates the virtual buffer for reading and structural navigation. The **JAWS Cursor** tracks the mouse pointer to reach areas the other cursors cannot. Users toggle between these with Insert+Z.

**Browse vs. forms mode**: In browse mode, letter keys are intercepted as navigation shortcuts — H jumps to headings, R to landmarks, T to tables, F to form fields, B to buttons, and so on. When focus enters a form control, JAWS auto-switches to **forms mode**, passing keystrokes to the application for typing and selection. Users exit forms mode to resume structural navigation. This mode switching is invisible to the application but fundamentally changes the user's available commands at any moment.

**Element navigation**: Single-letter shortcuts (with Shift for reverse) let the user jump between element types. The **elements list** (Insert+F3) opens a dialog listing all elements of a chosen type — links, headings, buttons, form fields — for rapid scanning without reading through content sequentially.

**Table navigation**: Once inside a table, Ctrl+Alt+Arrow keys move between cells. The user can read the current row, column, or cell in isolation. Column and row headers are announced with each cell if properly associated.

### NVDA

**Category**: screen_reader
**Platforms**: Windows
**Device context**: Desktop

Free and open-source screen reader by NV Access — widely used globally, especially outside North America. NVDA uses a modifier key (Insert by default, configurable to Caps Lock) for its commands.

**Browse vs. focus mode**: Like JAWS, NVDA operates in two modes. **Browse mode** intercepts keystrokes for structural navigation — H for headings, D for landmarks, K for links, F for form fields, B for buttons. **Focus mode** passes keystrokes to the application for form interaction. Toggle manually with Insert+Space, or NVDA auto-switches when focus enters or leaves form controls.

**Element navigation**: Single-letter shortcuts mirror JAWS in concept but differ in some key bindings (e.g., D for landmarks vs. R in JAWS; K for links vs. U in JAWS). The **Elements List** (Insert+F7) provides a unified dialog to browse headings, links, form fields, and landmarks.

**Text reading granularity**: The user can read by line (arrow keys), word (Ctrl+Left/Right), character (Left/Right), sentence (Alt+Up/Down), or paragraph (Ctrl+Up/Down). Continuous reading from the current position (Insert+Down) is how users consume body text.

**Learning aids**: NVDA offers a keyboard help mode (Insert+1) that announces what each key does without executing the action — useful for beginners learning navigation commands.

### VoiceOver (macOS)

**Category**: screen_reader
**Platforms**: macOS
**Device context**: Desktop

Built-in macOS screen reader. VoiceOver uses a **VO modifier** (Ctrl+Option) for all commands, which can be locked (VO+;) to avoid holding both keys continuously.

**No modal navigation**: Unlike Windows screen readers, VoiceOver does not switch between browse and focus modes. The **VoiceOver cursor** moves through elements and can interact with them directly — VO+Space activates any element (links, buttons, checkboxes, etc.) without mode switching.

**The Rotor**: VoiceOver's primary discovery and navigation tool. VO+U opens the Rotor, which displays categorised lists of interface elements — headings, links, form controls, landmarks, tables, images. The user switches categories with Left/Right arrows, selects an element with Up/Down, and jumps to it with Enter. The Rotor can be filtered by typing (e.g., "nav" to filter landmarks). This is how VoiceOver users get the structural overview that Windows SR users get through elements lists and single-letter shortcuts.

**Element-type navigation**: VO+Cmd+letter shortcuts jump to the next element of a type (H for headings, L for links, J for form elements, T for tables, G for graphics). Add Shift to go to the previous occurrence.

**Object interaction**: For complex controls and embedded content, VO+Shift+Down enters the object (interacting with its children) and VO+Shift+Up exits back to the parent level.

### Narrator

**Category**: screen_reader
**Platforms**: Windows
**Device context**: Desktop

Built-in Windows screen reader. Uses a **scan mode** for structural navigation (similar to browse mode in JAWS/NVDA) with the Narrator key (Caps Lock or Insert) as modifier. Frequently encountered as a secondary or fallback screen reader on machines without JAWS/NVDA installed. Increasingly capable but still has gaps for complex interactive interfaces compared to JAWS/NVDA.

### VoiceOver (iOS)

**Category**: screen_reader
**Platforms**: iOS
**Device context**: Mobile

Built-in iOS screen reader — the dominant mobile screen reader. Touch-based interaction: the user drags a finger across the screen to hear elements under the touch point, or swipes right/left to move through elements sequentially. Double-tap activates the focused element. The **rotor** (two-finger twist gesture) provides quick navigation by headings, links, form controls, landmarks, and other element types — functionally equivalent to the macOS Rotor but controlled by gesture. No physical keyboard assumed — all interaction through touch gestures. Typing uses the on-screen keyboard with touch-type or standard-typing mode.

### TalkBack

**Category**: screen_reader
**Platforms**: Android
**Device context**: Mobile

Built-in Android screen reader — predominantly used in regions where Android market share is higher. Linear navigation model: swipe right/left to move through elements sequentially, double-tap to activate. The **reading controls menu** (swipe up then right) provides navigation by headings, links, and controls — functionally similar to VoiceOver's rotor but with different gestures. Multi-finger gestures for scrolling (two-finger swipe) and global actions (two-finger tap for pause).

### Refreshable braille display

**Category**: braille_display
**Platforms**: Cross-platform, paired with screen reader

A significant minority of screen reader users use braille output, often alongside speech. Displays one line of braille at a time — common sizes are 40-cell (~40 characters) and 14-cell (portable, ~14 characters). The user reads character by character or word by word, revealing exact spelling, punctuation, and formatting that speech may gloss over. Routing buttons above each cell allow direct cursor placement. Deaf-blind users rely on braille as their sole output channel — all information must reach the braille display without requiring speech or audio cues.

## Exploration Strategies

### Heading navigation

The dominant navigation method for screen reader users. The user presses a quick-nav key to jump between headings, building a mental outline of the interface structure — this is the screen reader equivalent of a sighted user visually scanning the page. Experienced users navigate almost exclusively by headings; beginners are less likely to know this strategy.

**AT Mechanisms**: H / Shift+H (JAWS, NVDA), VO+Cmd+H (VoiceOver macOS), Rotor > Headings (VoiceOver iOS, TalkBack), Headings list (JAWS: Insert+F6, NVDA: Insert+F7, VoiceOver: Rotor)
**Device context**: All

**UI Requirements**: Properly nested heading hierarchy. Headings must be descriptive and reflect content groupings. Every visually distinct section should have a heading. Skipped heading levels create confusion about structure. One primary heading per page or view identifying the content.

### Find / search

The user invokes a find command and types a keyword to jump directly to matching text. This bypasses structure entirely and is effective when the user knows what they are looking for but not where it is. Beginners rely on this more than advanced users as a compensatory strategy when they don't know structural navigation shortcuts.

**AT Mechanisms**: Ctrl+F (system find), NVDA+Ctrl+F (NVDA find), Ctrl+F (JAWS virtual find)
**Device context**: Desktop

**UI Requirements**: Content must be real text, not rendered in images or canvas elements. Search results must be navigable and focus must move to matched content. Content that has not yet rendered (lazy-loaded) will not be found.

### Landmark navigation

The user jumps between named regions of the interface (navigation, main content, complementary, footer) to orient within the layout. A supplementary strategy that improves efficiency when landmarks are present — equivalent to a sighted user recognising the header, sidebar, and footer areas — but most users do not rely on it as their primary method.

**AT Mechanisms**: D / Shift+D (NVDA), R / Shift+R (JAWS), Rotor > Landmarks (VoiceOver)
**Device context**: All

**UI Requirements**: Distinct regions of the interface must be identifiable as landmarks. When multiple landmarks of the same type exist, each should have a unique accessible name to distinguish them. The main content area should be identifiable as the primary landmark.

### Tab-through interactive elements

The user presses Tab to move between focusable elements (links, buttons, inputs). Reveals the interactive controls available but skips static content. Beginners often rely on Tab as their primary navigation method. On mobile, swiping right/left through all elements sequentially serves a similar purpose.

**AT Mechanisms**: Tab / Shift+Tab (desktop), Swipe right / left (mobile), F key for form fields (JAWS, NVDA)
**Device context**: All

**UI Requirements**: Logical tab order matching visual flow. All interactive elements must be focusable. Custom controls must be in the tab order with appropriate roles. Focus must be managed correctly for dynamic content — when content appears, changes, or is dismissed, focus must move to or return from the appropriate element.

### Screen reader elements list

The user opens a dialog or rotor listing all elements of a given type — links, headings, form fields, or landmarks — allowing rapid scanning of available actions without reading through content sequentially. Element names must be meaningful out of context because they are presented in an isolated list ('click here' and 'read more' are indistinguishable).

**AT Mechanisms**: Insert+F7 (NVDA Elements List), Insert+F3 (JAWS), Rotor (VoiceOver — both desktop and mobile)
**Device context**: All

**UI Requirements**: Links and buttons must have descriptive accessible names that convey purpose when read in isolation. Avoid duplicate names for elements with different destinations or actions. Vague or redundant names make the elements list unusable.

### Sequential reading

The user reads through content linearly from top to bottom using arrow keys (desktop) or sequential swipe gestures (mobile). This is how screen reader users read body text, instructions, and unfamiliar content. All users fall back to sequential reading for consuming text; some beginners use it as their primary navigation method.

**AT Mechanisms**: Down / Up arrow (desktop browse mode), Swipe right / left (mobile sequential navigation)
**Device context**: All

**UI Requirements**: Reading order must reflect logical content order. Visual reordering that diverges from the underlying content order creates a confusing, non-sequential experience. Content should be meaningful when read linearly.

### Touch exploration

On mobile devices, the user drags a finger across the screen to hear elements under the touch point. This builds a spatial understanding of the layout through touch. Repeated visits let the user remember approximate positions and navigate more quickly.

**AT Mechanisms**: Touch-and-drag (VoiceOver, TalkBack), Double-tap to activate, Swipe gestures for navigation, Rotor / reading controls for element-type navigation
**Device context**: Mobile

**UI Requirements**: Touch targets must be large enough to discover via touch exploration. Elements must be properly labelled. Custom gestures must have single-pointer alternatives. Drag-and-drop must have accessible alternatives. No reliance on hover interactions.

### Form interaction *(from baseline)*

The user fills out forms by navigating between fields, typing, selecting from dropdowns, checking boxes, and submitting. On desktop, screen readers switch from browse mode to forms mode when entering a field, changing available keyboard commands. The user expects clear labels, required-field indicators, and immediate feedback on errors.

**AT Mechanisms**: Keyboard (typing), Tab (field navigation), Screen reader mode switching
**Device context**: All

**UI Requirements**: Every form field must have a persistent label (not only placeholder text). Required fields must be indicated. Error messages must be specific and associated with the relevant field. Successful submission must be confirmed.

### Navigation and wayfinding *(from baseline)*

The user navigates between pages or views using menus, breadcrumbs, links, and back/forward controls. They build a mental model of the application's structure. They expect to know where they are, where they can go, and how to get back.

**AT Mechanisms**: Screen reader navigation, Keyboard (Tab, Enter), Back/forward controls
**Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated. Important actions reachable from any page. Back navigation should work predictably.

### Touch / pointer interaction *(from baseline)*

The user taps, swipes, and uses gestures on a touchscreen. With a screen reader active, the standard touch model changes — single tap explores, double-tap activates. Touch targets must be large enough to hit accurately. Gestures must be discoverable and have single-pointer alternatives.

**AT Mechanisms**: Screen reader touch gestures, Swipe navigation
**Device context**: Mobile

**UI Requirements**: Touch targets large enough to discover and activate. No reliance on hover for essential information. Custom gestures must have single-pointer alternatives. Drag-and-drop must have tap-based alternatives.

## User Variants

### Desktop screen reader user

Navigates primarily by headings and uses landmark navigation, elements lists, and quick-nav keys fluently. Typically uses multiple screen readers (e.g., JAWS at work, NVDA at home) and expects consistent behaviour across them. Experienced users set speech rate very high and are frustrated by verbose or redundant announcements. They expect well-structured interfaces and standard keyboard interaction patterns for complex widgets (tabs, menus, dialogs, trees).

**Primary AT**: JAWS, NVDA, VoiceOver (macOS)
**Device context**: Desktop
**Preferred navigation**: Heading navigation, Landmark navigation, Screen reader elements list

**Expectations**:
- Fast, efficient navigation through well-structured heading hierarchy
- Predictable, consistent interaction patterns across pages and across screen readers
- Minimal verbosity — no redundant role announcements, no excessive decorative content
- Keyboard shortcuts that don't conflict with screen reader commands
- Dynamic content announced appropriately, not intrusively

### Mobile screen reader user

Navigates by swipe gestures and rotor/reading controls. Touch exploration replaces the mouse; there is no hover state and no physical keyboard assumed. May have limited patience for complex interfaces designed desktop-first. Expects responsive layouts that simplify rather than merely shrink the desktop experience.

**Primary AT**: VoiceOver (iOS), TalkBack
**Device context**: Mobile
**Preferred navigation**: Touch exploration, Sequential reading, Heading navigation (via rotor)

**Expectations**:
- Touch targets large enough to discover via touch exploration
- Swipe navigation that follows a logical order
- No reliance on hover interactions
- Responsive layouts that don't break screen reader navigation on mobile viewports
- Custom gestures have single-pointer alternatives

### Beginner screen reader user

May be recently blinded, ageing into vision loss, or new to assistive technology. Relies heavily on Tab key and sequential reading. May not know about heading navigation, landmark shortcuts, or elements lists. Needs clear, simple structures and explicit instructions. Lower speech rate. Gets disoriented easily by complex layouts.

**Primary AT**: NVDA, Narrator
**Device context**: All
**Preferred navigation**: Tab-through interactive elements, Sequential reading, Find / search

**Expectations**:
- Simple, linear content flow that makes sense read top to bottom
- Clear labels and instructions before form fields, not after
- Obvious affordances — controls that announce what they do
- Error messages that explain what went wrong and what to do next
- Forgiving interactions — easy to undo, confirm before destructive actions

### Braille display user

Reads output character by character on a refreshable braille display, revealing exact spelling, punctuation, and formatting that speech glosses over. May use braille alongside speech, or — in the case of Deaf-blind users — as the sole output channel where all information must reach the braille display without requiring audio.

**Primary AT**: Refreshable braille display paired with JAWS, NVDA, or VoiceOver
**Device context**: All
**Preferred navigation**: Sequential reading, Heading navigation

**Expectations**:
- Clean text content without decorative Unicode characters or excessive emoji
- Proper use of punctuation and formatting — braille reveals every character
- Tables with proper header associations (braille reads cell by cell)
- All interactive feedback available as text (not only as audio cues)

### New / infrequent user *(from baseline)*

Encountering the interface for the first time or after a long gap. Relies on labels and progressive disclosure to learn the interface. Cannot recall shortcuts or hidden features.

**Primary AT**: None
**Device context**: All
**Preferred navigation**: Navigation and wayfinding, Form interaction

**Expectations**:
- Interface is learnable without documentation
- Primary actions are obvious
- Error messages guide toward resolution
- Navigation structure is understandable

## Learning Considerations

- **First visit**: The user has no mental model of the interface. They will explore via headings and landmarks to understand the structure before attempting the task. Poor heading structure means the user may never find the relevant section. This initial orientation takes significantly longer than a sighted user's visual scan.

- **Habituating**: On repeat visits, the user builds expectations about where things are and how interactions behave. Inconsistency between pages (e.g., primary action button sometimes first, sometimes last in the tab order) forces re-learning.

- **Mode switching** (desktop): Screen readers have distinct modes — browse mode for reading and structural navigation, and forms/focus mode for interacting with controls. Entering a form field typically switches modes automatically, changing available keyboard commands. Poorly structured forms can cause confusing automatic mode switches or prevent the user from reaching instructions between fields.

- **Recovery from disorientation**: When something unexpected happens (an overlay appears, focus is lost, content changes dynamically), the user must re-orient. The assistive technology may not announce changes unless the interface explicitly communicates them. Interactive elements that don't behave as expected and content that changes without warning are among the most frustrating experiences.

- **Cognitive load of sequential access**: Sighted users can glance at a page and grasp the layout in seconds. A screen reader user must build this understanding piece by piece, sequentially. Complex layouts impose significant cognitive burden even on experienced users. Simplicity and clear structure directly reduce this load.

- **Desktop vs. mobile mental model differences**: Mobile navigation (swipe gestures, rotor) differs fundamentally from desktop (keyboard shortcuts, browse/focus mode). Users expect the interface to be coherent on both platforms but accept layout adaptations. Content that disappears or becomes inaccessible on mobile viewports is a failure.

- **Multi-screen-reader context switching**: Many users switch between screen readers with different key bindings and behaviours. Interfaces that rely on standard semantics and platform conventions survive this switching better than those that depend on workarounds for a specific screen reader.

- **First visit** *(from baseline)*: The user approaches the interface with expectations set by common platform conventions. Standard UI patterns (menus, search, tabs, dialogs) are recognised immediately. Non-standard patterns require learning.

- **Mental models** *(from baseline)*: Users build a model of how the interface works based on early interactions. If the model is violated later (e.g., a control that sometimes navigates and sometimes submits), trust erodes and the user becomes cautious and slower.

- **Error recovery** *(from baseline)*: All users occasionally make mistakes. The interface should make errors recoverable (undo, confirmation dialogs, clear error messages) rather than punishing. Irreversible actions without confirmation are universally problematic.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

System status feedback must be announced by the screen reader — visual-only indicators (colour changes, progress bars, spinners) are invisible. After user actions, status updates must reach the user through programmatic announcements or focus movement to the new content. Dynamic content that updates silently leaves the blind user unaware something happened. Rapid sequential announcements can interrupt each other, losing information.

### Heuristic 2 — Match Between System and Real World

Language and metaphors must make sense without a visual referent. Icon-only controls are meaningless without accessible names. All interactive elements need descriptive names that convey purpose out of context (they appear in elements lists in isolation). Spatial language ('click the button on the right', 'see the sidebar') should be supplemented with structural references.

### Heuristic 3 — User Control and Freedom

The user must be able to dismiss overlays, undo actions, and navigate back — all without vision. Focus must return to the trigger element when an overlay is dismissed. Authentication challenges that require vision block task completion entirely. Destructive actions need confirmation with focus management. On mobile, the standard dismiss gesture must work for overlays.

### Heuristic 4 — Consistency and Standards

Consistent heading structure, landmark patterns, and widget keyboard behaviour across pages and views. Users expect standard keyboard interaction patterns for complex widgets — tabs, menus, dialogs, trees. If a tab panel uses arrow keys on one page and Tab on another, the user's mental model breaks. Interfaces relying on standard semantics and platform controls behave consistently across different screen readers.

### Heuristic 5 — Error Prevention

Errors are expensive for screen reader users — re-reading forms, re-navigating to fields, and re-attempting input all take significantly longer than for sighted users. Provide clear constraints, format hints, and required-field indicators before input. Required indicators must be programmatically associated with the field, not conveyed only visually. Confirmation for destructive actions must be announced and focusable.

### Heuristic 6 — Recognition Rather than Recall

Labels, instructions, and context must be programmatically associated with their controls — the user cannot rely on visual spatial proximity. Breadcrumbs, page titles, and region labels help the user know where they are without seeing the layout. Form fields need persistent labels (not only placeholder text, which disappears on input).

### Heuristic 7 — Flexibility and Efficiency of Use

Efficiency is paramount — the user cannot visually skip to content. Heading navigation, landmark navigation, keyboard shortcuts, and skip links in web pages help experienced users work efficiently. Multiple navigation strategies should be supported simultaneously. On mobile, the rotor provides equivalent efficiency for element-type navigation. Long sequences of Tab presses or swipes to reach primary content are a significant barrier.

### Heuristic 8 — Aesthetic and Minimalist Design

Verbosity is the enemy of efficiency. Redundant role announcements, excessive decorative content that gets announced, overly verbose status announcements, and too many links or navigation items all slow the user down. Every element the screen reader announces is something the user must listen to or swipe through. Streamline: fewer controls, descriptive names, decorative content hidden from assistive technology.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Error messages must be programmatically associated with their fields, announced by the screen reader, and actionable. An error summary is useful only if it provides navigation to the offending fields. Inline validation must announce errors as they occur. The user must be able to understand what went wrong, where, and how to fix it — sequentially, not visually.

### Heuristic 10 — Help and Documentation

Help content must be accessible to screen readers — no text in images, proper heading structure, navigable contents. Complex workflows need orientation cues (step indicators, progress announcements). Search is a critical navigation fallback for users who cannot visually scan. On mobile, help should be reachable without complex gesture sequences.
