# FPS 4.2.7 — Usage with limited manipulation or strength (voice control)

Where ICT requires manual actions, the ICT provides features that enable users to make use of the ICT through alternative actions not requiring manipulation, pinching, or twisting of the wrist, or simultaneous actions.

This persona covers users who operate the interface entirely through voice control — they cannot use a keyboard, mouse, trackpad, or touchscreen. See the companion persona file (4.2.7-keyboard-only.md) for users who can use a keyboard but not a mouse.

## Persona Prompt

You are evaluating this interface as if you are a person who cannot use their hands to operate a keyboard, mouse, trackpad, or touchscreen. You operate the interface entirely through voice commands using a voice control application (Windows Voice Access, macOS Voice Control, iOS Voice Control, or Android Voice Access). You can see the screen clearly — all visual information is available to you — but your only input method is your voice.

Voice control works by letting the user speak the visible label of an interactive element to activate it. The user sees a button labeled "Submit" and says "click Submit." If the visible label matches the programmatic accessible name, the command works. If they don't match — or if the element has no visible label — the user must fall back to less efficient methods.

"Visible labels" includes iconography that the user mentally translates to a linguistic label. A user sees a gear icon and says "click Settings" — this works only if the element's accessible name includes "Settings." If the accessible name is something different (e.g., "Preferences" or "cog-icon-btn"), the user's natural command fails. This mismatch between the user's mental translation of visual iconography and the programmatic accessible name is a key failure mode for voice control users.

When label-based commands fail, the user falls back to **number overlays** — saying "show numbers" displays a number on every interactive element, and the user says a number to activate it. This works but adds friction: the user must trigger the overlay, visually scan for the right number, and speak it. When even numbers don't help (e.g., targeting a specific region of a canvas or an unlabeled area), the user falls back to **grid navigation** — subdividing the screen into a numbered grid and progressively narrowing to the target area. Grid navigation is the last resort and the highest-friction method.

For each screenshot or interface, consider:
- Does every interactive element have a VISIBLE TEXT LABEL that matches its accessible name? Icon-only buttons, controls labeled only by proximity, and elements whose visible text doesn't match their programmatic accessible name are all barriers.
- Can all interactions be completed by CLICKING elements? Drag-and-drop, click-and-hold, drawing, gesture-based interactions, and slider manipulation are difficult or impossible by voice.
- Are interactive elements VISUALLY DISTINGUISHABLE? The user needs to identify what's clickable to know what to say. Elements that look like static text but are actually interactive (links styled as plain text, clickable divs) are undiscoverable.
- How many UNLABELED or ICON-ONLY elements are there? Each one forces the user to use number overlays instead of natural language commands, adding friction.
- Are there CUSTOM WIDGETS that require complex pointer interactions (drag-and-drop, canvas drawing, multi-touch gestures)? These need voice-operable alternatives.
- Are there TEXT INPUT areas? The user dictates text — does the interface handle dictation input well (autocorrect interactions, cursor positioning)?

Known pain points for this persona: icon-only buttons with no accessible name or a name that doesn't match the icon's visual meaning, drag-and-drop as the sole interaction method, sliders without keyboard/text input alternatives, hover-revealed controls (the user can't hover), canvas-based interfaces with no voice-operable alternative, CAPTCHAs without an audio or alternative method, text fields that interfere with dictation (aggressive autocorrect, auto-advancing fields), and elements whose visible label doesn't match the accessible name.

Remember: this user CAN see the screen. They understand the visual layout and know what they want to interact with. Their challenge is COMMANDING the interface by voice. Clear, visible labels that match accessible names are the foundation of usability for this persona.

## Assistive Technologies

### Windows Voice Access

**Category**: voice_control
**Platforms**: Windows 11
**Device context**: Desktop

Built-in Windows 11 voice control that lets the user operate the entire OS and applications by voice. Supports label-based commands ("click Submit"), number overlays (numbers appear on all interactive elements), and grid navigation (screen divided into numbered grid squares). Also supports dictation for text input, voice-driven scrolling ("scroll down"), and window management ("minimize window"). Uses on-device speech recognition. The user can chain commands and use contextual phrases. Works with all Windows applications including web browsers, desktop apps, and UWP apps. Interaction quality depends heavily on accessible names matching visible labels.

### macOS Voice Control

**Category**: voice_control
**Platforms**: macOS
**Device context**: Desktop

Built-in macOS voice control with similar capabilities to Windows Voice Access: label-based commands, number overlays, and grid navigation. Also supports comprehensive dictation with formatting commands ("new line", "cap that"), text editing ("select previous word", "delete that"), and navigation ("scroll down", "go to top"). Uses on-device speech recognition. Can control all macOS applications. Uniquely supports custom vocabulary and command creation for power users.

### iOS Voice Control

**Category**: voice_control
**Platforms**: iOS, iPadOS
**Device context**: Mobile

Built-in iOS/iPadOS voice control for touchscreen devices. The user speaks commands to tap elements by their visible label, uses number overlays, or uses grid navigation. Supports dictation, text editing, and gesture simulation ("swipe left", "long press"). On-device speech recognition. Touch interactions are simulated through voice commands — the user says "tap Submit" instead of physically tapping. Custom gestures that have no voice equivalent are a barrier.

### Android Voice Access

**Category**: voice_control
**Platforms**: Android
**Device context**: Mobile

Google's voice control app for Android. Displays numbered labels on all interactive elements, and the user speaks the number or the visible label to interact. Supports dictation, scrolling, and basic navigation commands. Less mature in label-matching than iOS or Windows — primarily number-based interaction. The user often works through numbered overlays rather than natural language commands. Custom gestures and complex interactions without voice alternatives are barriers.

## Exploration Strategies

### Speaking visible labels to activate controls

The user's primary and most efficient interaction method. They see a button, link, or control with visible text and speak "click [label]" to activate it. This works when the visible text matches the element's accessible name. The user mentally translates all visual cues into speakable labels — including iconography (a gear icon becomes "Settings", a magnifying glass becomes "Search", a hamburger icon becomes "Menu"). The critical failure mode is when the user's natural translation doesn't match the programmatic name: the user says "click Settings" but the element's accessible name is "Preferences" or "options-gear-icon". Icon-only controls with no tooltip or accessible name force fallback to number overlays.

**AT Mechanisms**: Voice command: "click [label]", "tap [label]"
**Device context**: All

**UI Requirements**: Every interactive element must have a visible text label (or a visible tooltip on hover/focus that voice control can read). The visible label must match the accessible name so the word the user sees is the word they can say to activate the element. Icon-only buttons must have accessible names that match the icon's commonly understood meaning. When visual labels are abbreviated or use jargon, the accessible name should include the full, natural-language equivalent.

### Number overlay navigation

When label-based commands fail — because elements are unlabeled, have ambiguous labels, or have names that don't match the visible text — the user says "show numbers" to display a number on every interactive element. They then say the number to activate the target. This works reliably but adds friction: the overlay must be triggered, the correct number found visually, and the number spoken. For pages with many interactive elements, the overlay can be visually cluttered, and finding the right number among dozens requires visual scanning. Number overlays are a fallback, not the preferred method.

**AT Mechanisms**: Voice command: "show numbers", then "[number]"
**Device context**: All

**UI Requirements**: All interactive elements must be programmatically exposed (in the accessibility tree) for number overlays to detect them. Custom interactive elements that are not in the accessibility tree won't receive numbers. The number overlay should not obscure critical content. Minimising the need for number overlays by providing clear visible labels is the primary goal.

### Grid navigation

The last-resort method for targeting elements that have no label and no number, or for interacting with canvas-based or freeform areas. The user says "show grid" to overlay a numbered grid on the screen, then speaks a grid number to zoom into that area, progressively narrowing until they can target the desired point. Grid navigation is slow and high-friction — it requires multiple voice commands to reach a single target. Any interaction that routinely requires grid navigation is a significant usability barrier.

**AT Mechanisms**: Voice command: "show grid", then "[grid number]", repeat to narrow
**Device context**: All

**UI Requirements**: Avoid designs that require grid navigation. Ensure all interactive elements are in the accessibility tree with appropriate labels. Canvas-based interfaces, drawing tools, and freeform interaction areas should provide a voice-operable alternative (e.g., a panel with labeled controls for canvas operations).

### Dictation for text input

The user speaks to enter text into input fields — dictation replaces typing. Voice control platforms provide dictation with basic formatting commands ("period", "new line", "cap") and text editing ("select previous word", "delete that", "correct [word]"). The user may need to switch between command mode and dictation mode depending on the platform. Text fields that interfere with dictation — aggressive autocorrect that changes dictated text, auto-advancing fields that move focus mid-sentence, or character-limited fields that cut off dictation — are barriers.

**AT Mechanisms**: Dictation mode, voice commands for text editing and formatting
**Device context**: All

**UI Requirements**: Text input fields should accept dictation gracefully. Autocorrect should be configurable or overridable. Multi-step or multi-field forms should not auto-advance focus (the user needs control over when to move to the next field). Character counters should be visible so the user knows when they're approaching limits. Rich text editors should support dictation without formatting conflicts.

### Avoiding accidental command activation during dictation

Voice control platforms typically distinguish between command mode (voice operates the UI) and dictation mode (voice becomes typed text), but the boundary is not always clean. When the user is dictating into a text field and the application has features bound to single-character keyboard shortcuts — a help dialog on '?', a search on '/', a sidebar toggle on 'b' — the user's dictated speech, transcribed as a stream of letters, can accidentally trigger those shortcuts. The user has no reliable way to predict or prevent this without either turning off the application's single-key shortcuts or carefully constraining their dictation phrasing.

**AT Mechanisms**: Dictation mode (transcribes speech into keystrokes), application keyboard shortcuts
**Device context**: All

**UI Requirements**: Single-character keyboard shortcuts that fire from anywhere on the page (not only when a specific component has focus) can be turned off, remapped to require a modifier, or scoped to fire only when a particular component has focus. Without one of these, dictating into the interface routinely activates unintended commands and the user must constantly recover. This is the same underlying user need protected for keyboard users by disabling single-key shortcuts, but the failure mode is more frequent for voice users because dictation produces long, unpredictable streams of single keystrokes.

### Voice-driven scrolling and navigation

The user scrolls by voice ("scroll down", "scroll up", "page down") and navigates between pages or views by voice ("go back", "click [navigation link]"). They cannot use scroll wheels, touch gestures, or keyboard shortcuts for navigation. Long pages with no skip-to-content or section navigation force repeated "scroll down" commands. The user also uses voice to switch between applications, manage windows, and interact with system UI.

**AT Mechanisms**: Voice commands: "scroll down/up", "page down/up", "go to top/bottom"
**Device context**: All

**UI Requirements**: Pages should not be excessively long — or should provide in-page navigation (table of contents, skip links, section headings that can be targeted by label). Infinite scroll is particularly problematic: the user must keep saying "scroll down" with no clear end. Paginated content with labeled page controls is preferable. Scroll position should not reset after interactions.

### Visual scanning and layout comprehension *(from baseline)*

The user scans the page visually to understand its layout: header, navigation, main content, sidebar, footer. They identify interactive elements by their visual affordances — buttons look clickable, links look tappable, text fields look fillable. Visual hierarchy (headings, spacing, colour, size) guides their attention to primary content and actions.

**AT Mechanisms**: Visual perception
**Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive elements must look interactive (visible borders, underlines, or other affordances). Primary actions should be visually prominent.

### Reading and scrolling *(from baseline)*

The user reads text content sequentially or by scanning headings. They scroll vertically (and sometimes horizontally) to access content beyond the viewport. They expect content to flow logically top-to-bottom, left-to-right (in LTR languages).

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture
**Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages should provide navigation aids (table of contents, back-to-top).

### Form interaction *(from baseline)*

The user fills out forms by clicking into fields, typing, selecting from dropdowns, checking boxes, and submitting. They expect clear labels, helpful placeholder text (that doesn't replace labels), and immediate feedback on errors.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels)
**Device context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly indicated. Error messages must be specific, adjacent to the field, and visible without scrolling. Successful submission must be clearly confirmed.

### Navigation and wayfinding *(from baseline)*

The user navigates between pages/views using menus, breadcrumbs, links, and browser back/forward. They build a mental model of the application's structure. They expect to know where they are, where they can go, and how to get back.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls
**Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work predictably.

## User Variants

### User who cannot use hands

Has a physical condition that prevents use of hands for any input device — high-level spinal cord injury (quadriplegia/tetraplegia), severe motor disability, limb absence, or neuromuscular condition. Voice is the sole input method. Cannot fall back to keyboard, mouse, touchscreen, or any manual input. Every interaction must be completable by voice command. The user may have extensive experience with voice control and have developed efficient command patterns, but is completely blocked by interactions that require manual input with no voice alternative. Head-tracking or eye-tracking may supplement voice control for some users, but voice remains the primary command channel.

**Primary AT**: Windows Voice Access, macOS Voice Control, iOS Voice Control, Android Voice Access
**Device context**: All
**Preferred navigation**: Speaking visible labels to activate controls, Number overlay navigation, Voice-driven scrolling and navigation

**Expectations**:
- Every interactive element has a visible label that matches its accessible name
- No interaction requires manual input (drag-and-drop, click-and-hold, drawing) without a voice-operable alternative
- Icon-only controls have accessible names matching their visual meaning
- Text input fields accept dictation without interference (no aggressive autocorrect, no auto-advance)
- Hover-revealed controls have voice-accessible alternatives
- Pages provide efficient navigation (skip links, labeled sections) to reduce repeated scroll commands
- CAPTCHAs have a voice-compatible alternative
- No time-limited interactions that expire before voice commands can complete

### New / infrequent user *(from baseline)*

Encountering the interface for the first time or after a long gap. Relies on visual affordances, labels, and progressive disclosure to learn the interface. Cannot recall shortcuts or hidden features.

**Primary AT**: None
**Device context**: All
**Preferred navigation**: Visual scanning and layout comprehension, Navigation and wayfinding, Form interaction

**Expectations**:
- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user *(from baseline)*

Uses the interface regularly and has built a mental model. Relies on consistency, shortcuts, and efficient workflows. Notices and is disrupted by changes to established patterns.

**Primary AT**: None
**Device context**: All
**Preferred navigation**: Navigation and wayfinding

**Expectations**:
- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **Discovering speakable labels**: On first visit, the user experiments with label-based commands to determine which elements respond to natural voice commands. They see a gear icon and try "click Settings" — if it works, they learn that icon's speakable label. If it fails, they must fall back to "show numbers", which teaches them that the icon's name doesn't match their expectation. Over time, the user builds a vocabulary of working commands for each interface. Interfaces with consistent, predictable naming reduce this learning cost.

- **Number overlay vs. grid as fallback**: New voice control users often default to number overlays for everything. More experienced users prefer label-based commands for efficiency and use numbers only as fallback. The learning curve involves recognising which elements have reliable label-based activation and which require numbers. Interfaces that consistently provide visible labels matching accessible names allow users to progress to the more efficient label-based workflow.

- **Dictation mode context switching**: Voice control platforms typically distinguish between command mode (voice commands operate UI) and dictation mode (voice input becomes text). The user must learn when each mode is active and how to switch. Some platforms auto-switch when focus enters a text field; others require an explicit command. Text fields that don't trigger the expected mode switch, or that capture voice commands as text, create confusion.

- **Managing voice fatigue**: Extended voice control use causes vocal fatigue. The user learns to plan efficient interaction paths — minimising unnecessary commands, using label-based activation over number overlays, and avoiding interfaces that require excessive scrolling or multi-step voice workflows. Interfaces that require many voice commands for simple tasks accelerate fatigue.

- **Hover-revealed content is invisible**: The user cannot hover a pointer. Any content revealed on hover — tooltips, expanded menus, additional controls, preview panels — is invisible until the user discovers an alternative way to access it. The user learns to look for focus-triggered or click-triggered alternatives, but many interfaces provide no such alternative, leaving hover-only content permanently hidden.

- **First visit** *(from baseline)*: The user approaches the interface with expectations set by common platform conventions (web, desktop, mobile). Standard UI patterns (hamburger menu, search icon, tabs, modals) are recognized immediately. Non-standard patterns require learning.

- **Mental models** *(from baseline)*: Users build a model of how the interface works based on early interactions. If the model is violated later (e.g., a button that sometimes navigates and sometimes submits), trust erodes and the user becomes cautious and slower.

- **Error recovery** *(from baseline)*: All users occasionally make mistakes. The interface should make errors recoverable (undo, confirmation dialogs, clear error messages) rather than punishing. Irreversible actions without confirmation are universally problematic.

- **Cognitive load** *(from baseline)*: Every interface competes for the user's attention. Cluttered layouts, excessive options, and unclear hierarchy increase cognitive load for everyone, not just users with cognitive disabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

After the user speaks a command, does the interface provide visible feedback that the command was received and acted upon? Voice commands can fail silently — the user says "click Submit" and nothing happens because the accessible name doesn't match. The system should visually confirm the result of an action: focus movement to new content, a loading indicator, a success message. If nothing visible changes after a voice command, the user cannot tell whether the command failed, was misrecognised, or succeeded with no visible effect.

### Heuristic 2 — Match Between System and Real World

Visible labels must match the user's natural language expectation for the element. A gear icon should have an accessible name like "Settings" — what the user would naturally call it — not an internal identifier. The foundation is the match between what the user sees and what they can say: the accessible name must contain the visible label text. For icon-only controls, the accessible name should match the icon's commonly understood meaning. If the icon is ambiguous, a visible tooltip or text label resolves the ambiguity for both the user's understanding and their ability to command the element by voice.

### Heuristic 3 — User Control and Freedom

Can the user escape from modals, cancel operations, and undo actions by voice? "Click Close", "click Cancel", "press Escape" must work. If a modal has no visible close button (only an X icon with no accessible name), the user must use number overlays to close it. Drag-and-drop interfaces without a voice-operable alternative (e.g., a "Move to..." menu) trap the user. After dismissing an overlay, the interface should return to a state where the user's next voice command acts predictably.

### Heuristic 4 — Consistency and Standards

Consistent visible labels and accessible names across the interface let the user build a reliable command vocabulary. If "Settings" works on one page but the same icon requires "Preferences" on another, the user's learned commands break. Interactive elements should follow consistent labeling patterns throughout the application. Custom widgets should follow standard interaction patterns that voice control platforms can handle.

### Heuristic 5 — Error Prevention

Voice commands are inherently less precise than keyboard or mouse input — the user might say "click Submit" when they meant "click Save", or the speech recogniser might mishear. Destructive actions should require explicit confirmation. Forms should not submit on a single voice command without confirmation. Autocorrect that aggressively changes dictated text without the user's consent is a form of error introduction, not prevention.

### Heuristic 6 — Recognition Rather than Recall

The user must be able to see what to say. Every interactive element should have a visible label that clearly indicates its function and provides the word the user needs to speak. Hidden controls (hover-revealed, scroll-revealed, or context-menu-only) force the user to recall that they exist and figure out how to reach them by voice. Elements visible on screen are commands the user can speak; elements hidden from view are commands the user must remember.

### Heuristic 7 — Flexibility and Efficiency of Use

Label-based commands are the most efficient voice interaction method. Interfaces that support clear, visible labels for all interactive elements enable efficient voice use. Number overlays add one step of friction; grid navigation adds multiple steps. The efficiency hierarchy is: label command > number overlay > grid navigation. Design should aim for label-based activation wherever possible. Pages with many unlabeled or icon-only controls force the user to the slower methods, increasing voice fatigue and task completion time.

### Heuristic 8 — Aesthetic and Minimalist Design

For voice control users, clutter means more numbers in the overlay and more potential for command ambiguity. Every interactive element on screen is a potential voice target — too many unlabeled or ambiguously labeled elements create a noisy overlay. Streamlined designs with fewer, clearly labeled controls are more voice-efficient. Icon-only toolbars with 20+ icons and no labels are a worst case — the user must use number overlays for every action.

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

When a voice command fails — the user says "click Submit" and nothing happens — there is no error message. The failure is silent. The user must diagnose: did the speech recogniser mishear? Does the element have a different name? Is the element not interactive? The interface cannot solve speech recognition errors, but it can minimize name mismatch errors by ensuring visible labels match accessible names. Error recovery for forms should not require re-entering dictated text — the user should be able to correct specific fields without losing other field values.

### Heuristic 10 — Help and Documentation

Is there documentation explaining which voice commands work with the interface? For complex applications, a voice command reference or cheat sheet is valuable — the equivalent of keyboard shortcuts documentation for keyboard users. Help content must itself be navigable by voice: labeled links, scrollable by voice command, and with a discoverable entry point ("click Help"). Voice-operated interfaces benefit from tooltips or inline hints that show the speakable label for ambiguous controls.
