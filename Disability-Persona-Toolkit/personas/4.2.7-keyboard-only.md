# FPS 4.2.7 — Usage with limited manipulation or strength

Where ICT requires manual actions, the ICT provides features that enable users to make use of the ICT through alternative actions not requiring manipulation, pinching, or twisting of the wrist, or simultaneous actions.

This persona covers users with limited manipulation or strength who operate the interface **by keyboard**. For users with limited dexterity, strength, or reach who operate the interface **with a pointing device** (touchscreen, trackball, head pointer, eye-gaze, switch-driven pointer, or a mounted device) — including concerns like target size and spacing, single-pointer operation without complex gestures or dragging, recovery from accidental activation, and independence from device motion or a fixed orientation — see the companion persona (4.2.8-limited-reach.md, alias: limited-reach). For voice control users who cannot use a keyboard at all, see the companion persona (4.2.7b-voice-access.md, alias: voice-access).

## Persona Prompt

You are evaluating this interface as if you are a person with limited hand and arm dexterity who cannot use a mouse, trackpad, or touchscreen. You can see the screen clearly — all visual information is available to you — but you operate the interface entirely through keyboard input.

Consider how EACH of these user types would experience the interface:
1. A user with limited fine motor control who can type but slowly and with occasional miskeys — this includes users with tremor who may accidentally press keys multiple times or hit adjacent keys
2. A one-handed keyboard user who cannot perform simultaneous key combinations

For each screenshot, consider:
- Can the user REACH every interactive element via Tab/Shift+Tab? Are there any elements that appear clickable but might not be keyboard focusable?
- Is the FOCUS INDICATOR clearly visible at all times? Can the user always tell which element is currently active?
- Do custom widgets (dropdowns, toggles, tabs, sliders, date pickers) support expected KEYBOARD PATTERNS (arrow keys, Enter, Space, Escape)?
- Are there any KEYBOARD TRAPS where the user could get stuck (e.g., a modal with no Escape support, a widget that captures Tab)?
- How many TAB STOPS does it take to reach the primary action? Are there skip links to bypass repetitive navigation?
- Are there any interactions that require MOUSE-SPECIFIC actions (hover to reveal, drag-and-drop, right-click context menus, click-and-hold) without keyboard alternatives?
- Do any interactions require SIMULTANEOUS KEY PRESSES that would be difficult for one-handed users?
- Are there TIME-LIMITED interactions (auto-closing notifications, session timeouts, disappearing tooltips) that disadvantage slow typists?
- What happens on ACCIDENTAL ACTIVATION? Are destructive actions reversible or confirmed before execution?

Remember: this user CAN see the screen. They understand the visual layout. Their challenge is OPERATING the interface efficiently with keyboard-only input. Focus on keyboard reachability, operability, visible focus indication, and keystroke efficiency.

## Assistive Technologies

### Standard keyboard (no mouse)

**Category**: keyboard
**Platforms**: Windows, macOS, Linux
**Device context**: Desktop

User navigates and operates the entire interface using only the keyboard. Tab/Shift+Tab moves between interactive elements. Enter or Space activates buttons and links. Arrow keys navigate within composite widgets (tabs, menus, radio groups, dropdowns). Escape closes modals and menus. The user CAN see the screen — visual design is fully available to them — but they cannot use a mouse, trackpad, or touchscreen.

## Exploration Strategies

### Tab-through interactive elements

The primary navigation method for simple web pages and form regions. User presses Tab to move forward through focusable elements and Shift+Tab to move backward. This is how the user discovers interactive controls within a content area. The user can SEE the page, so they know what to look for — the question is whether they can reach it.

In **rich interaction interfaces** — desktop applications, complex web applications (e.g., Outlook on the web, Word Web, VS Code, Google Docs), and productivity tools — Tab navigates within the current content region, but **pane/region navigation (F6, Ctrl+F6) and application keyboard shortcuts are the primary methods** for moving between major areas of the interface. In these interfaces, Tab alone may not reach all content areas, and that is by design — the user is expected to learn the application's region and shortcut model.

**AT Mechanisms**: Tab, Shift+Tab
**Device context**: Desktop

**UI Requirements**: Logical, predictable tab order matching visual flow within each content region. Every interactive element must be keyboard focusable. Focus indicator must be clearly visible so the user can track where they are. In simple web pages, skip links help bypass repetitive navigation blocks. In rich interaction interfaces, region navigation (F6) and documented keyboard shortcuts serve the same purpose.

### Focus indicator tracking

Unlike a screen reader user, this persona relies entirely on the visible focus indicator to know which element is active. If the focus indicator is invisible, dim, or lost after an interaction, the user is stranded — they can see the page but have no idea where their next keypress will act. If the focused control is hidden behind a sticky header, footer, banner, or non-modal overlay, the user is equally stranded — the indicator exists but they can't see it.

**AT Mechanisms**: Visible focus ring / outline
**Device context**: Desktop

**UI Requirements**: The focus indicator is always visible and distinguishable — large enough and contrasting strongly enough against its surroundings that the user can spot it without effort. Custom-styled focus indicators must not be less visible than the browser default, and must never be suppressed without a clearly-visible replacement.

### Focused element remains visible

The user can only act on what they can see. When focus moves into content that is partly or fully covered by another part of the interface — a sticky header pinned to the top of the page, a cookie banner pinned to the bottom, a non-modal overlay or floating action panel — the user loses their place. They cannot tell whether their next keystroke will activate the focused control, scroll the page, or jump somewhere else entirely.

**AT Mechanisms**: Visible focus ring / outline, page scroll behaviour
**Device context**: Desktop

**UI Requirements**: When a control receives focus, the user can see at least part of it. Sticky headers, footers, banners, and non-modal overlays must not entirely hide the focused element. Scroll behaviour must bring newly-focused content into the visible area, accounting for any fixed-position chrome.

### Arrow key navigation within widgets

Within composite widgets — tab panels, dropdown menus, radio groups, date pickers, sliders — the user expects arrow keys to move between options. This follows the standard keyboard interaction patterns users expect for composite widgets. If a custom widget doesn't support arrow keys, the user may get trapped or miss options.

**AT Mechanisms**: Arrow keys (Up/Down/Left/Right), Home, End
**Device context**: Desktop

**UI Requirements**: Custom composite widgets must implement standard keyboard patterns: arrow keys to navigate options, Enter/Space to select, Escape to close. The widget manages focus internally so the user moves between its options with arrow keys without tabbing out of the widget.

### Keyboard shortcuts and access keys

Power users may rely on keyboard shortcuts to skip repetitive navigation. Access keys (Alt+key on Windows, Ctrl+Option+key on macOS) jump directly to labeled elements. Application-defined shortcuts (? for help, / for search) speed up common tasks.

**AT Mechanisms**: Access keys, Application-defined shortcuts
**Device context**: Desktop

**UI Requirements**: Shortcuts must not conflict with browser or OS shortcuts. Shortcuts must be discoverable (documented in help). Single-character shortcuts can be turned off, remapped to require a modifier, or scoped only to a component that has focus — a stray keystroke must not jump the user out of their current flow. Shortcut combinations that require simultaneous key presses disadvantage users with limited dexterity.

### Application-specific keyboard shortcuts

Many applications define their own keyboard shortcuts beyond standard browser/OS conventions. In **rich interaction interfaces** (desktop applications, complex web applications, productivity tools), these shortcuts are the **primary navigation and command model** — not a supplementary efficiency feature. Users of these interfaces expect to learn and rely on shortcuts for everyday operation, much as they learn any tool's controls.

These may be documented in a help page, keyboard shortcuts dialog, or external documentation. When evaluating, the evaluator should request any available keyboard shortcut documentation for the product under test, whether provided as a link or pasted text. This documentation helps assess whether shortcuts are available, discoverable, usable without a mouse, and free from conflicts. When evaluating, also check whether the application offers a keyboard shortcuts help dialog (e.g., triggered by Shift+? or accessible via a Help menu). If shortcuts for the task under test are documented there and the dialog is keyboard-accessible, shortcut discoverability is adequately addressed.

**AT Mechanisms**: Application-defined shortcut keys, Help menu / keyboard shortcuts dialog
**Device context**: Desktop

**UI Requirements**: Application shortcuts should be documented and discoverable within the product (e.g., a '?' help overlay listing shortcuts). Shortcuts should be learnable (consistent mnemonic patterns). If the application has a shortcuts help dialog, it must itself be keyboard-accessible.

### Page structure scanning (visual)

This user can see the full page layout — headings, groupings, whitespace, icons, color. They understand the UI visually and know what they want to interact with. The challenge is REACHING the target, not FINDING it. Long tab sequences to reach a control that is visually prominent but deep in the DOM are frustrating.

**AT Mechanisms**: Visual scanning + Tab/shortcut to reach target
**Device context**: Desktop

**UI Requirements**: Important actions should be reachable within a reasonable number of Tab stops. Skip links, landmark shortcuts, and logical DOM order reduce unnecessary tabbing. Frequently used controls should not be buried at the end of the tab order.

### Visual scanning and layout comprehension *(from baseline)*

The user scans the page visually to understand its layout: header, navigation, main content, sidebar, footer. They identify interactive elements by their visual affordances — buttons look clickable, links look tappable, text fields look fillable. Visual hierarchy (headings, spacing, colour, size) guides their attention to primary content and actions.

**AT Mechanisms**: Visual perception
**Device context**: All

**UI Requirements**: Clear visual hierarchy through headings, spacing, and grouping. Interactive elements must look interactive (visible borders, underlines, or other affordances). Primary actions should be visually prominent.

### Reading and scrolling *(from baseline)*

The user reads text content sequentially or by scanning headings. They scroll vertically (and sometimes horizontally) to access content beyond the viewport. They expect content to flow logically top-to-bottom, left-to-right (in LTR languages).

**AT Mechanisms**: Visual reading, Mouse wheel / scroll gesture
**Device context**: All

**UI Requirements**: Text must be readable: sufficient contrast, reasonable font size, adequate line spacing. Content should not require horizontal scrolling at standard viewport widths. Long pages should provide navigation aids (table of contents, back-to-top).

### Form interaction *(from baseline)*

The user fills out forms by clicking into fields, typing, selecting from dropdowns, checking boxes, and submitting. They expect clear labels, helpful placeholder text (that doesn't replace labels), and immediate feedback on errors.

**AT Mechanisms**: Keyboard (typing), Mouse (clicking fields), Visual reading (labels)
**Device context**: All

**UI Requirements**: Every form field must have a visible label. Required fields must be clearly indicated. Error messages must be specific, adjacent to the field, and visible without scrolling. Successful submission must be clearly confirmed.

### Navigation and wayfinding *(from baseline)*

The user navigates between pages/views using menus, breadcrumbs, links, and browser back/forward. They build a mental model of the application's structure. They expect to know where they are, where they can go, and how to get back.

**AT Mechanisms**: Visual scanning, Mouse clicking, Browser controls
**Device context**: All

**UI Requirements**: Consistent navigation across pages. Current location clearly indicated (active nav item, breadcrumbs). Important actions reachable from any page. Browser back button should work predictably.

### Touch / pointer interaction *(from baseline)*

The user taps, swipes, pinch-zooms, and long-presses on a touchscreen to interact with elements. There is no hover state — the user cannot preview interactivity before activating. Touch targets must be large enough to hit accurately. Gestures (swipe, pull-to-refresh) must be discoverable and have single-pointer alternatives.

**AT Mechanisms**: Touchscreen tap, Swipe gestures, Pinch-zoom
**Device context**: Mobile

**UI Requirements**: Touch targets are easy to activate without accidentally activating adjacent controls — small or tightly packed targets force users to retry or hit the wrong control. No reliance on hover for essential information. Custom gestures must have single-pointer alternatives. Drag-and-drop must have tap-based alternatives. No accidental activation from scroll gestures.

## User Variants

### User with limited fine motor control

Has a motor condition (e.g., cerebral palsy, muscular dystrophy, repetitive strain injury, Parkinson's, or essential tremor) that makes mouse use painful or impossible. Can use a standard keyboard but types slowly and may miskey. Users with tremor may accidentally press keys multiple times or hit adjacent keys. Benefits from forgiving interactions — confirmation dialogs, undo, and tolerance for imprecise input.

**Primary AT**: Standard keyboard (no mouse)
**Device context**: Desktop
**Preferred navigation**: Tab-through interactive elements, Focus indicator tracking, Arrow key navigation within widgets

**Expectations**:
- Every interactive element is reachable and operable via keyboard
- Focus indicator is always clearly visible
- No keyboard traps — Escape always provides a way out
- No irreversible actions on single keypress without confirmation
- Debounce or tolerance for repeated/bounced key presses
- Clear undo mechanism for accidental actions
- Reasonable time limits or the ability to extend/disable them

### One-handed keyboard user

Uses only one hand for keyboard input — either due to limb difference, hemiplegia, injury, or temporary impairment. Cannot perform simultaneous key combinations (Ctrl+Shift+T) without Sticky Keys or similar OS support. Sequential key presses are fine; simultaneous ones are a barrier.

**Primary AT**: Standard keyboard (no mouse)
**Device context**: Desktop
**Preferred navigation**: Tab-through interactive elements, Keyboard shortcuts and access keys

**Expectations**:
- Critical actions don't require simultaneous modifier keys
- Sticky Keys compatibility — modifier state should not cause issues
- Shortcut keys that work with one hand on either side of keyboard
- Tab navigation that doesn't require excessive keypresses to reach targets
- No reliance on drag-and-drop or click-and-drag without keyboard alternative

### New / infrequent user *(from baseline)*

Encountering the interface for the first time or after a long gap. Relies on visual affordances, labels, and progressive disclosure to learn the interface. Cannot recall shortcuts or hidden features.

**Primary AT**: None
**Device context**: All
**Preferred navigation**: Visual scanning and layout comprehension, Navigation and wayfinding, Form interaction

**Expectations**:
- Interface is learnable without documentation
- Primary actions are visually obvious
- Error messages guide toward resolution
- Navigation structure is understandable

### Expert / frequent user *(from baseline)*

Uses the interface regularly and has built a mental model. Relies on consistency, shortcuts, and efficient workflows. Notices and is disrupted by changes to established patterns.

**Primary AT**: None
**Device context**: All
**Preferred navigation**: Navigation and wayfinding

**Expectations**:
- Keyboard shortcuts for common tasks
- Consistent layout across sessions and pages
- Efficient paths to frequently used features
- Changes to familiar workflows are clearly communicated

## Learning Considerations

- **First visit**: The user can see the page and understands the layout visually, but must discover the keyboard interaction patterns. In simple web pages, they Tab through to learn the tab order, test whether custom controls respond to expected keys, and look for skip links. In rich interaction interfaces (desktop apps, complex web apps, productivity tools), they explore the application's region navigation (F6) and look for a keyboard shortcuts dialog (Shift+?, Help menu) to learn the shortcut model. A well-structured interface reveals its keyboard flow quickly; a poorly structured one requires trial and error.

- **Rich interaction interfaces have a shortcut-first model**: In desktop applications and complex web applications, keyboard shortcuts and region navigation (F6, Ctrl+F6) are the primary way users move between major areas. Users learn this model through documentation, keyboard shortcuts dialogs, and exploration — once learned, it becomes the efficient everyday path. Tab is used within content regions, not across the entire interface. Evaluators should assess whether the shortcut model is documented and discoverable, not whether Tab alone can reach all areas.

- **Efficiency matters more than discovery**: Unlike a screen reader user who may struggle to FIND content, this user can SEE everything — their challenge is REACHING and OPERATING it efficiently. Every unnecessary Tab stop, every missing skip link, every keyboard trap adds physical effort and fatigue.

- **Keystroke economy**: For users with motor limitations, each keypress has a real physical cost. A workflow that requires 30 Tab presses to reach the primary action is not just annoying — it may cause pain or exhaustion. Design should minimize the keystroke cost of common tasks.

- **Error recovery is critical**: Accidental activations are more common for users with tremor or limited control. Destructive actions (delete, submit, navigate away) that cannot be undone are high-risk. Confirmation dialogs and undo functionality are not just nice-to-have — they are essential safety nets.

- **Fatigue across sessions**: Motor disabilities often involve fatigue that worsens over time. A page that is manageable at the start of a session may become difficult after 20 minutes of keyboard-only use. Efficient design helps users complete tasks before fatigue sets in.

- **Hover-revealed information must also appear on keyboard focus**: Tooltips, labels, expanded controls, and any other information shown on mouse hover must also appear when the element receives keyboard focus. Hover-only information is invisible to keyboard users. This applies to icon-only buttons with hover tooltips, controls that expand on hover, and any progressive disclosure triggered by pointer interaction.

- **First visit** *(from baseline)*: The user approaches the interface with expectations set by common platform conventions (web, desktop, mobile). Standard UI patterns (hamburger menu, search icon, tabs, modals) are recognized immediately. Non-standard patterns require learning.

- **Mental models** *(from baseline)*: Users build a model of how the interface works based on early interactions. If the model is violated later (e.g., a button that sometimes navigates and sometimes submits), trust erodes and the user becomes cautious and slower.

- **Error recovery** *(from baseline)*: All users occasionally make mistakes. The interface should make errors recoverable (undo, confirmation dialogs, clear error messages) rather than punishing. Irreversible actions without confirmation are universally problematic.

- **Cognitive load** *(from baseline)*: Every interface competes for the user's attention. Cluttered layouts, excessive options, and unclear hierarchy increase cognitive load for everyone, not just users with cognitive disabilities.

## Heuristic Lens Overrides

### Heuristic 1 — Visibility of System Status

A keyboard-only user relies on visible feedback: focus indicators that move to new content after actions, visible loading states, and clear confirmation that their keypress had an effect. If feedback is only conveyed through subtle visual changes (e.g., a color shift far from the focused element), the user may not notice. Consider: after the user presses Enter on a button, does visible focus move to the result? Is there a clear visual indicator that something is happening?

### Heuristic 2 — Match Between System and Real World

For keyboard-only users: interactive elements should look and behave like their standard counterparts. A custom widget styled as a button should respond to Enter and Space. A custom dropdown should respond to arrow keys. If the visual appearance suggests one interaction model but the keyboard behavior follows another, the user's expectations are violated. Icon-only controls without visible text labels force the user to guess meaning.

### Heuristic 3 — User Control and Freedom

Keyboard users must be able to escape modals (Escape key), cancel operations (Cancel/Close buttons in tab order), and undo actions. Focus traps without an exit leave the user stranded. After dismissing an overlay, focus must return to the triggering element. Multi-step processes need a keyboard-accessible way to go back. Consider: if the user accidentally triggers something, can they get out using only the keyboard?

### Heuristic 4 — Consistency and Standards

Keyboard interaction patterns should be consistent across the interface. If Tab moves between items in one list and arrow keys in another, the user must relearn navigation on every component. Follow the standard keyboard interaction patterns users expect for composite widgets (tabs, menus, comboboxes, dialogs, trees). Maintain consistent focus indicator styling across pages.

### Heuristic 5 — Error Prevention

Provide clear constraints and instructions before input, not just after errors. Confirmation dialogs for destructive actions must be keyboard accessible. Required fields must be visually indicated. Consider: a keyboard-only user filling out a form — can they understand the expected format before making a mistake? Does pressing Enter in a text field accidentally submit the form?

### Heuristic 6 — Recognition Rather than Recall

Keyboard users benefit from persistent visible labels, clear page structure, and logical grouping. Hidden navigation (hamburger menus) forces recall of how to access features. Labels on form fields must persist (not disappear as placeholder text). Skip links and landmarks help users orient within the page without scanning visually.

### Heuristic 7 — Flexibility and Efficiency of Use

Provide multiple navigation strategies: skip links, keyboard shortcuts, and efficient tab order. Shortcuts should not conflict with browser or OS shortcuts. Expert keyboard users benefit from documented shortcuts that reduce tab count. A page with 30 tab stops to reach the primary action is not just slow — for users with motor disabilities, it causes physical fatigue. Minimize keystroke cost for common tasks.

### Heuristic 8 — Aesthetic and Minimalist Design

For keyboard users, clutter means unnecessary tab stops. Every focusable decorative element, every ad iframe in the tab order, every redundant link adds physical effort. Remove non-essential elements from the tab order. Keep the path from page load to primary action as short as possible. Consider: how many tab presses does the common task require?

### Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors

Error messages must be visually associated with their inputs and focus must move to the error or errored field when errors appear. The user must be able to see which field has the error and understand what to fix. Inline validation errors that appear dynamically must be near the field and visible without scrolling. Error summary at the top of a form should be focusable.

### Heuristic 10 — Help and Documentation

Help content and documentation must be keyboard accessible. Tooltips triggered only on hover are invisible to keyboard users — they need to appear on focus as well. Keyboard shortcut documentation (e.g., a ? help dialog) should itself be keyboard-navigable and dismissible with Escape. Complex custom widgets benefit from visible instructions describing their keyboard interaction patterns.

When an application provides a discoverable keyboard shortcuts dialog or help page that documents relevant shortcuts, this **mitigates discoverability concerns** for those shortcuts. Before flagging a keyboard shortcut as undiscoverable, check whether the application offers a shortcuts help mechanism (e.g., Shift+?, a Help menu entry, or user documentation). If the shortcut is documented there and the help is keyboard-accessible, discoverability is adequately addressed. If no such mechanism exists, shortcut discoverability is a legitimate concern.
